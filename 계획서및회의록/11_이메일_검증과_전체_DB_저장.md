# 이메일 검증과 전체 DB 저장

## 적용 내용

회원가입 시 화면과 서버가 같은 이메일 규칙을 적용한다.

- 허용 예: `hunter@gmail.com`, `hunter@naver.com`, `first.last+quest@company.co.kr`.
- 거부 예: `da@ee`, `da@.com`, `da@mail..com`, `da@-mail.com`, `da..ee@gmail.com`.
- 이메일 앞뒤 공백을 제거하고 소문자로 저장한다. 특정 메일 제공자로 제한하지 않는다.
- 이메일 형식 검사이며 실제 메일함의 존재·사용 권한을 확인하는 인증 메일은 아직 구현하지 않았다.
- 이전에 가입한 형식이 잘못된 계정은 삭제하지 않았으며 기존 로그인은 유지한다.

기존 서버는 회원·물품·매칭 알림을 이미 MySQL에 저장했다. 반환·QR·경험치·활동 알림과 업로드 사진도 서버 저장으로 전환했다. 홈과 프로필에서도 브라우저 예시 데이터를 사용하지 않는다.

## 저장 위치

현재 로컬 DB는 프로젝트용 MySQL의 `lost_quest`이며, 개발 프로필의 `ddl-auto=update`로 다음 테이블을 준비한다.

| 테이블 | 저장하는 기록 |
| --- | --- |
| `users` | 이메일, 닉네임, BCrypt 비밀번호 해시, 권한 |
| `lost_items` | 회원의 분실물, 등록자, 사진 경로, 반환 상태 |
| `found_items` | 회원의 습득물, 등록자, 사진 경로, 소유 확인 질문과 답변 해시, 반환 상태 |
| `match_notifications` | 매칭 후보와 읽음 상태 |
| `return_requests` | 요청자, 습득물, 연결한 분실물, 진행 단계, QR 코드·유효기간·사용 시각 |
| `experience_events` | 계정별 경험치 지급 기록, 중복 방지용 이벤트 키 |
| `activity_notifications` | 물품 등록·반환 활동 소식과 읽음 시각 |
| `item_images` | 서버가 만든 파일 이름과 이미지 바이트 |

프로필 닉네임은 `users`, 등록·반환 횟수는 물품·반환 기록, XP는 지급 기록을 조회한다. 레벨과 업적은 이 DB 기록에서 계산하므로 별도 브라우저 저장이 필요하지 않다.

새 사진은 물품과 같은 DB 트랜잭션에 저장되며 실패 시 함께 롤백된다. 이전 디스크 사진은 조회 시 DB에 복사하고 원본 파일은 유지한다. 아직 조회하지 않은 예전 사진이 있다면 원본 업로드 폴더도 보관해야 한다.

로그인 토큰은 기존처럼 브라우저 탭의 `sessionStorage`에 남는다. 경찰청 공공데이터는 외부 API로 조회하며 우리 DB에 전체 원본을 복제하지 않는다.

## 반환 이용 방법

서로 다른 요청자 계정과 습득자 계정으로 진행한다.

1. 습득자가 습득물 등록 시 소유 확인 질문과 비공개 답변을 입력한다. 이전에 등록한 습득물은 상세 화면에서 질문을 설정할 수 있다.
2. 요청자가 습득물 상세에서 반환을 요청한다. 매칭 추천에서 이동하면 본인의 분실물도 연결된다.
3. 요청자가 소유 확인 질문에 답한다. 서버가 해시와 비교하며 정답은 다른 사용자에게 응답하지 않는다.
4. 습득자가 반환 관리(`/admin`)에서 승인한다. 관리 권한은 해당 습득물 등록자 또는 DB의 `ADMIN` 사용자에게 있다.
5. 요청자가 반환 화면에서 QR 또는 인증 코드를 습득자에게 제시한다.
6. 습득자가 QR 내용을 읽어 인증 코드 입력칸에 입력하거나 붙여 넣는다. 현재 화면에는 카메라 스캐너가 없으며 서버가 입력된 코드를 검증한다.
7. 습득자가 반환 관리에서 최종 완료한다. 연결된 분실물과 습득물이 반환 완료로 바뀌고 습득자에게 50 XP가 지급된다.

QR은 30분간 유효하며 한 번만 사용할 수 있다. 만료 시 습득자가 재발급한다. 같은 완료 요청을 여러 번 또는 동시에 전송해도 반환 XP는 한 번만 지급된다. 물품 등록 보상은 등록자에게 10 XP이며, 새로 등록하는 기록부터 지급 내역을 남긴다.

직접 등록한 습득물에 자신의 반환 요청을 만들거나 다른 회원의 분실물을 연결할 수 없다. 요청자·습득자·관리자만 반환 기록을 볼 수 있다.

## DBeaver 확인

Host `127.0.0.1`, Port `3306`, Database `lost_quest`, Username `lostquest_app`을 사용한다. 비밀번호는 `backend/application-local.yml`의 DB 비밀번호와 같아야 한다. 프로젝트 DB 실행 방법은 [macOS 전체 실행 가이드](10_macOS_전체_실행_가이드.md)를 참고한다.

DBeaver에서 연결을 새로고침한 뒤 다음을 실행한다.

```sql
USE lost_quest;
SHOW TABLES;

SELECT id, email, nickname, role FROM users;
SELECT id, user_id, title, status FROM lost_items;
SELECT id, user_id, title, status, ownership_question FROM found_items;
SELECT id, requester_id, found_item_id, lost_item_id, status,
       qr_expires_at, qr_used_at FROM return_requests;
SELECT user_id, event_key, amount FROM experience_events;
SELECT id, user_id, title, read_at FROM activity_notifications;
SELECT filename, OCTET_LENGTH(content) AS image_bytes FROM item_images;
```

## 기존 기록과 검증 결과

기존 MySQL 회원·물품·매칭 알림은 유지했다. 확장 전 DB 백업은 로컬 `.local/schema-backups/before-account-storage-20261010.sql`에 저장했다.

기존 브라우저 체험 기록은 로그인 계정과 연결되지 않고 고정 예시 XP·반환 이력을 포함하므로 자동 이관하지 않았다. 브라우저 저장소 자체를 삭제하지는 않았고, 새 화면에서는 사용하지 않는다. 이를 실제 계정에 가져오려면 소유자를 지정하고 예시 기록을 걸러내는 별도 이관이 필요하다.

2026-10-10 확인:

- 백엔드 전체 277개 테스트 성공: 이메일, 기존 물품·매칭, 반환 단계·권한, QR 만료·재발급, 경험치 중복 방지, 사진 저장·롤백.
- 프론트엔드 전체 239개 테스트와 빌드 성공: 화면 이메일 검증, 서버 API 호출, 계정 전환 시 이전 계정의 기록 차단.
- 실제 MySQL·HTTP 검증: `da@ee` 400, 정상 가입·로그인, 사진 포함 등록, 반환·QR·XP 저장 및 재조회, 읽음 저장.
- 실제 완료 요청 두 개의 동시 전송에서 XP 한 번 지급 확인.
- 검증용 회원·물품·반환·사진은 정리했다. 기존 회원 2명·분실물 1건·매칭 알림 5건은 전후 동일했다.
- DBeaver UI 연결은 별도로 수행해야 한다. MySQL 쿼리와 서버 응답으로 저장을 확인했다.
