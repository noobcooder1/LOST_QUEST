# LOST QUEST 발표자료 개발 기록

## 03. 회원가입 및 로그인

### 구현 목적

기존 프론트엔드 프로토타입의 데모 인증을 실제 백엔드와 데이터베이스를 사용하는 인증 구조로 전환하였다.

사용자가 회원가입 및 로그인한 뒤 JWT를 이용하여 인증 상태를 유지하고,
백엔드에서 인증된 사용자를 식별할 수 있도록 구현하였다.

---

### 주요 구현

- 이메일 기반 회원가입
- BCrypt 비밀번호 암호화 저장
- 로그인 및 JWT Access Token 발급
- Bearer Token 기반 인증
- `/api/auth/me`를 통한 현재 사용자 조회
- USER / ADMIN 역할 정보 처리
- React 인증 상태 연동
- sessionStorage 기반 Access Token 관리
- 인증 및 Validation 오류 응답 처리
- 로그인/회원가입 비밀번호 UTF-8 72바이트 제한

### 인증 구조

회원가입:

React
→ POST /api/auth/signup
→ AuthController
→ AuthService
→ UserRepository
→ MySQL

로그인:

React
→ POST /api/auth/login
→ 사용자 인증
→ JWT Access Token 발급
→ sessionStorage 저장

인증 요청:

React
→ Authorization: Bearer {token}
→ Spring Security
→ JWT 검증
→ 인증된 API 접근

사용자 확인:

GET /api/auth/me
→ JWT 사용자 식별
→ DB 사용자 조회
→ 사용자 정보 반환

### 핵심 구현 및 설계

#### 1. Stateless JWT 인증

서버 세션 대신 JWT Access Token을 사용하는 Stateless 인증 방식을 적용하였다.

로그인 성공 시 서버가 JWT를 발급하고,
프론트엔드는 이후 인증이 필요한 요청에 다음 헤더를 포함한다.

Authorization: Bearer {token}

Access Token의 기본 만료 시간은 1시간으로 설정하였다.

---

#### 2. 비밀번호 보호

사용자의 비밀번호는 평문으로 저장하지 않고 BCrypt로 해시하여 MySQL에 저장한다.

로그인 시 입력한 비밀번호와 저장된 BCrypt 해시를 비교하여 인증한다.

존재하지 않는 이메일에 대해서도 dummy BCrypt 연산을 수행하여
계정 존재 여부에 따른 응답 시간 차이를 줄이도록 구현하였다.

---

#### 3. JWT Secret 관리

JWT 서명에 사용하는 Secret은 소스 코드에 직접 저장하지 않는다.

환경변수 또는 Git에서 제외된 `application-local.yml`을 통해 주입하도록 구성하였다.

Secret이 없거나 요구되는 길이를 충족하지 못하면 서버 시작 단계에서 실패하도록 하여
잘못된 JWT 설정으로 애플리케이션이 실행되는 것을 방지하였다.

---

#### 4. 권한 처리

일반 회원가입을 통해 생성되는 사용자의 역할은 항상 USER로 지정한다.

클라이언트가 회원가입 요청을 조작하여 ADMIN 권한을 직접 지정할 수 없도록 하였다.

현재 ADMIN 계정 생성 API는 구현하지 않았으며,
실제 관리자 API를 구현하기 전에 DB의 현재 UserRole을 기준으로 권한을 검증하도록 개선할 예정이다.

---

#### 5. 프론트엔드 인증 상태 관리

Access Token은 브라우저의 sessionStorage에 저장한다.

애플리케이션 시작 시 `/api/auth/me`를 호출하여 현재 인증 상태를 확인하며,
인증 실패 시 저장된 인증 정보를 정리한다.

Refresh Token 및 서버 측 Token Blacklist는 현재 범위에는 포함하지 않았다.

---

### 입력 검증 강화

BCrypt는 비밀번호 입력 길이에 72바이트 제한이 있기 때문에
회원가입과 로그인 모두 UTF-8 기준 72바이트 이하인지 Validation 단계에서 검사하도록 구현하였다.

문자 수가 아니라 실제 UTF-8 바이트 수를 계산하기 때문에
한글과 같은 멀티바이트 문자도 동일한 기준으로 검증할 수 있다.

공통 `BcryptPasswordLimit` 로직을 사용하여 회원가입과 로그인에 동일한 규칙을 적용하였다.

---

### 보안 리뷰 과정에서 확인한 사항

보안 리뷰 과정에서
"로그인 비밀번호가 BCrypt의 72바이트 제한을 초과하면 예외가 발생하여 HTTP 500으로 처리될 수 있다"는 가능성이 제기되었다.

그러나 프로젝트에서 사용하는 `spring-security-crypto 6.5.11` 환경에서 직접 재현한 결과,
`BCryptPasswordEncoder.matches()`는 해당 입력에서 예외를 발생시키지 않고 `false`를 반환하여
기존 로그인 응답은 500이 아닌 401 INVALID_CREDENTIALS임을 확인하였다.

따라서 기존 500 오류를 수정한 것이 아니라,
라이브러리 내부 동작에 의존하지 않도록 애플리케이션 Validation 단계에서
UTF-8 기준 72바이트 제한을 명시적으로 적용하였다.

이를 통해 잘못된 입력은 BCrypt 처리 이전에 HTTP 400 VALIDATION_ERROR로 처리된다.

### BCrypt 경계값 테스트

UTF-8 바이트 기준 경계값을 별도로 검증하였다.

- 한글 24자 = 72바이트 → 허용
- ASCII 72바이트 → 허용
- ASCII 73바이트 → 400 VALIDATION_ERROR
- 한글 25자 = 75바이트 → 400 VALIDATION_ERROR
- ASCII 71자 + 한글 1자 = 74바이트 → 400 VALIDATION_ERROR

오류 응답에 입력한 비밀번호 평문이 포함되지 않는 것도 확인하였다.

### 문제와 해결

#### 문제 1. 기존 로컬 설정에서 JWT Secret 누락

인증 기능 구현 이전에 생성된 `application-local.yml`에는 JWT 설정이 존재하지 않아
새 인증 코드 적용 후 서버 시작에 실패할 수 있었다.

#### 해결

README에 기존 로컬 설정을 사용하는 개발자를 위한 JWT 설정 추가 방법을 문서화하였다.
실제 Secret 값은 Git이나 문서에 포함하지 않았다.

---

#### 문제 2. Spring Boot JAR 파일 잠금

기존에 실행 중이던 Java 프로세스가 JAR 파일을 사용하고 있어
Maven 패키징 과정에서 JAR 교체에 문제가 발생하였다.

#### 해결

기존 서버 프로세스를 종료한 뒤

mvnw clean package

를 다시 실행하여 정상적인 실행 JAR 생성을 확인하였다.
