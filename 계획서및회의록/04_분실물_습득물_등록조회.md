# LOST QUEST 발표자료 개발 기록

## 04. 분실물 / 습득물 등록 및 조회

### 구현 목적

기존 프론트엔드 프로토타입에서 브라우저의 `localStorage`(demoStore)에만 저장되던 자체 등록 물품을
Spring Boot REST API와 MySQL에 저장되는 실제 데이터로 전환하였다.

로그인한 사용자가 분실물/습득물을 등록하면 서버가 JWT로 작성자를 확인해 DB에 저장하고,
누구나 전국 검색과 상세 화면에서 실제 등록 데이터를 조회할 수 있도록 구현하였다.

---

### 주요 기능

- 분실물 등록 `POST /api/lost-items` (로그인 필요)
- 습득물 등록 `POST /api/found-items` (로그인 필요)
- 분실물/습득물 목록 조회 `GET /api/lost-items`, `GET /api/found-items` (공개)
- 분실물/습득물 상세 조회 `GET /api/lost-items/{id}`, `GET /api/found-items/{id}` (공개)
- 등록 전용 Request DTO와 서버 Validation
- JWT 인증 사용자를 등록 물품의 작성자로 자동 연결
- 물품 상태(LOST / STORED)를 서버에서 자동 지정
- 지역(region) 정보 DB 저장
- React 등록 화면 → 실제 API 등록
- React 검색 화면 → 자체 등록 물품을 실제 API에서 조회
- React 상세 화면 → 서버 물품은 상세 API로 조회

이번 단계에서 **수정/삭제, 이미지 업로드, 경찰청 공공데이터 API, AI 매칭, 반환 기능의 서버 연동은 구현하지 않았다.**

### API 흐름

등록:

React 등록 화면
→ POST /api/lost-items (Authorization: Bearer {token})
→ Spring Security JWT 검증
→ LostItemController
→ LostItemService
→ JWT subject(사용자 ID)로 User 조회
→ LostItemRepository
→ MySQL INSERT
→ 201 Created + 등록 물품 DTO

조회:

React 검색 화면
→ GET /api/lost-items, GET /api/found-items (토큰 없이 공개)
→ Service
→ Repository
→ MySQL SELECT
→ DTO 목록
→ 프론트엔드 Item 모델로 변환 후 기존 검색/필터 UI에 표시

상세:

/items/api-lost-12
→ GET /api/lost-items/12
→ 없으면 404 → "이 물품을 찾을 수 없어요" 화면

### 인증 사용자와 등록 물품 연결 방식

클라이언트가 `userId`를 보내는 구조를 사용하지 않았다.

JWT
→ Spring Security Authentication
→ JWT subject(사용자 ID)
→ `UserRepository`로 실제 User 조회
→ `LostItem.user` / `FoundItem.user`에 연결

등록 Request DTO에는 `userId`, `status`, `imageUrl` 필드 자체가 없다.
클라이언트가 이 값을 JSON에 넣어 보내도 무시되며, 테스트로 다음을 확인하였다.

- 다른 사용자의 `userId`를 넣어도 작성자는 JWT 사용자
- `status: "RETURNED"`를 넣어도 분실물은 `LOST`, 습득물은 `STORED`
- `imageUrl`에 data URL을 넣어도 DB에는 `NULL`

JWT는 유효하지만 DB에 해당 사용자가 없는 경우(탈퇴 등)는
기존 `AuthenticationFailedException`과 `ApiError` 형식을 재사용해 **401**로 응답한다.

### 핵심 구현 및 설계

#### 1. Entity와 분리된 등록 전용 DTO

Entity를 요청 본문으로 직접 받지 않고 `CreateLostItemRequest`, `CreateFoundItemRequest`를 만들었다.

서버 Validation 규칙:

- 물품명: 필수, 100자 이하
- 종류: `지갑 / 전자기기 / 가방 / 액세서리 / 기타` 중 하나
- 색상: 필수, 30자 이하
- 상세 설명: 10자 이상 2000자 이하
- 날짜: 필수, 미래 날짜 금지(`@PastOrPresent`)
- 지역: 17개 광역 지역(`서울`, `경기` 등) 중 하나
- 상세 장소: 필수, 200자 이하

모든 제한은 기존 Entity 컬럼 길이 안에 있도록 정했다.

---

#### 2. 지역(region) 데이터 모델

프론트엔드는 `지역(서울, 경기 …)`과 `상세 장소`를 분리해 입력받고,
검색 필터와 매칭 규칙이 `region` 값을 사용한다.
반면 기존 백엔드 Entity에는 `location`만 있었다.

`location` 문자열에 지역을 합치면 검색 필터가 동작하지 않거나 문자열 파싱에 의존하게 되므로,
`lost_items`, `found_items`에 **`region VARCHAR(20)` 컬럼을 추가**하였다.

- 기존에 저장된 행이 있어도 안전하게 추가되도록 DB 컬럼은 NULL 허용
- 새 등록은 DTO Validation으로 region을 필수로 검사
- 개발 프로필(`ddl-auto=update`)에서는 서버 시작 시 자동 추가됨을 실제 MySQL에서 확인
- `validate` 모드 DB용 `ALTER TABLE` 문을 README에 기록

---

#### 3. 서버 물품과 기존 데모 데이터의 식별자 분리

프론트엔드 `Item.id`는 문자열이고, seed 데모 물품은 `found-wallet-1` 같은 ID를 사용한다.
서버의 분실물/습득물은 서로 다른 테이블이라 숫자 ID가 겹칠 수 있다.

따라서 서버 물품의 화면 ID를 `api-lost-12`, `api-found-7` 형식으로 만들었다.

- 분실물 12번과 습득물 12번이 충돌하지 않음
- 정규식으로 파싱하여 seed ID가 서버 ID로 오인되지 않음
- 상세 화면은 이 ID로 어느 API를 호출할지 결정

---

#### 4. 데이터 출처 구분

| 출처 | 데이터 | 화면 표시 |
| --- | --- | --- |
| 자체 등록 | Spring Boot + MySQL | LOST QUEST |
| 공공데이터 | 기존 가상 seed 데이터 | 공공데이터 · 예시 |
| 체험 예시 | 기존 seed의 자체 등록 예시 | LOST QUEST · 체험 |

검색 화면에는 **서버 데이터 + 공공데이터 seed**만 표시한다.
기존 seed의 자체 등록 예시 물품은 반환·매칭 데모에 사용되므로 삭제하지 않고,
홈 화면·매칭·반환 체험 흐름에서 계속 사용할 수 있도록 유지하였다.

다음 단계에서 공공데이터 seed만 경찰청 OpenAPI로 교체할 수 있는 구조이다.

#### 5. 프론트엔드 API 계층

`services/itemApi.ts`에 물품 API 호출과 모델 변환을 모았다.

- 기존 `apiRequest`를 재사용하여 타임아웃, 오류 형식(`ApiError`) 처리를 공유
- 등록 요청에는 `sessionStorage`의 Access Token을 `Authorization: Bearer` 헤더로 전송
- 서버 응답을 검증한 뒤 기존 화면의 `Item` 타입으로 변환
- 공개 조회 요청에는 토큰을 붙이지 않음

#### 6. 등록 화면 UX

기존 3단계 등록 UI와 디자인은 유지하고 저장 방식만 서버 API로 바꾸었다.

- 등록 중 버튼 비활성화와 "등록 중…" 표시
- 실패 시 입력값 유지, 필드별 서버 검증 메시지 표시
- 401이면 기존 인증 정책대로 로컬 인증 정보를 정리하고 "로그인이 만료되었어요" 안내
- 성공 시 서버가 만든 실제 등록 번호와 상세 화면 링크 표시

### 문제와 해결

#### 문제 1. 빠른 중복 제출 시 같은 물품이 2건 저장됨

브라우저에서 실제 등록 흐름을 확인하던 중,
같은 순간에 등록 요청이 두 번 발생하면 MySQL에 같은 물품이 2건 저장되는 것을 발견하였다.

원인은 중복 제출 방지에 React state(`submitting`)만 사용했기 때문이다.
state 변경은 다시 렌더링된 뒤에 반영되므로, 그 사이의 두 번째 제출이 막히지 않았다.

#### 해결

`useRef` 기반의 동기 플래그를 추가하여 첫 요청이 끝나기 전의 제출을 즉시 무시하도록 수정하였다.
수정 후 같은 조건에서 3번 연속 제출해도 1건만 저장되는 것을 실제 DB에서 확인하였다.

---

#### 문제 2. 기존 권한 테스트와 새 등록 API의 충돌

기존 인증 테스트는 "인증된 사용자라도 허용되지 않은 API는 403"을 확인하기 위해
`POST /api/lost-items`를 사용하고 있었는데, 이번에 이 API가 정상 등록 API가 되었다.

#### 해결

테스트 목적(허용되지 않은 API의 403)을 유지하면서,
아직 제공하지 않는 수정 요청 `PUT /api/lost-items/1`로 검증 대상을 변경하였다.

---

#### 문제 3. 지역 정보 저장 위치

프론트엔드의 지역 필터와 백엔드의 `location` 단일 필드가 맞지 않았다.

#### 해결

지역을 문자열에 합치는 임시 방식 대신 별도 `region` 컬럼을 추가하고,
기존 데이터와의 호환을 위해 NULL을 허용하되 새 등록에서는 필수로 검증하였다.

### 현재 제한사항

- 수정/삭제 API 없음
- 이미지 업로드 없음: 서버 물품은 종류별 기본 이미지로 표시
- 서버 측 검색 필터/페이지네이션 없음: 목록 전체를 받아 프론트에서 필터링
- 서버 물품은 반환 요청·AI 매칭 데모와 아직 연결되지 않음
- 마이페이지 "내가 등록한 물품"은 아직 서버 데이터를 표시하지 않음
- 등록 XP 보상은 서버 등록에 적용하지 않음 (XP 기능 확장은 범위 밖)
- 로그인 만료(401) 시 작성 중이던 입력값은 다시 로그인하면 유지되지 않음
- 미래 날짜 판단은 서버 JVM 시간대 기준 (배포 서버가 UTC면 한국 시간 오전에 당일 날짜가 거부될 수 있어 배포 시 시간대 설정 필요)

### 발표에서 강조할 점

화면에서 등록 버튼을 누르면 실제로

React
→ JWT 인증
→ Spring Boot
→ MySQL

에 저장되고, 다시 조회되는 **실서비스 데이터 흐름**을 완성하였다.

특히 작성자를 클라이언트가 보내지 않고 **서버가 JWT로 결정**하도록 설계하여
다른 사용자로 위장한 등록이나 상태 조작을 구조적으로 막았다.

또한 테스트만 통과시키는 데 그치지 않고 실제 브라우저와 DB로 확인하는 과정에서
중복 제출 문제를 발견하고 수정한 사례를 개발 과정으로 소개할 수 있다.
