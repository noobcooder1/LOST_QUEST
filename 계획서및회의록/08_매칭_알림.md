# LOST QUEST 발표자료 개발 기록

## 08. 매칭 알림

### 1. 구현 목적

07단계의 매칭 추천은 사용자가 매칭 화면을 **직접 열어야만** 후보를 볼 수 있었다.
또 마이페이지의 "알림"은 반환 체험(데모)이 브라우저에 저장하는 가상 메시지뿐이었다.

이번 단계에서는 **내 분실물과 닮은 습득물이 새로 발견되면 LOST QUEST 안에서 알려 주는** 실제 서버 기능을 만들었다.

```
습득물 등록 / 로그인·알림 화면의 새 매칭 확인
→ 기존 매칭 엔진으로 점수 계산 (분류·지역·색상·날짜, 100점)
→ 70점 이상의 새 후보만 알림 저장 (MySQL, 중복 불가)
→ 헤더 알림 배지 + 마이페이지 알림 목록
→ 알림 클릭 → 습득물 상세 / 매칭 추천 화면
```

### 2. 주요 기능

| 기능 | 내용 |
| --- | --- |
| 알림 생성 | 대상 분실물, 매칭된 습득물, 출처(LOST QUEST / 경찰청), 매칭 점수, 생성 시각, 읽음 여부 |
| 알림 목록 | 내 알림 최신순, 읽지 않은 개수 함께 반환 |
| 읽음 처리 | 개별 읽음(멱등) / 모두 읽음 |
| 읽지 않은 개수 | 헤더 벨 아이콘 배지(99+), 마이페이지 "알림" 탭 숫자 |
| 이동 | 알림 클릭 → 읽음 처리 후 습득물 상세(`/items/api-found-{id}`, `/items/police-found-{atcId}-{fdSn}`) 또는 매칭 추천(`/matches?item=api-lost-{id}`) |
| 문구 | "등록한 ‘검정 지갑’과 유사한 습득물이 발견되었습니다." / "매칭도 92점 · 경찰청" |

API (모두 JWT 인증 필요, 사용자는 토큰에서만 결정):

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| GET | `/api/notifications?limit=30` | 내 알림 목록(1~100) + `unreadCount` |
| GET | `/api/notifications/unread-count` | 읽지 않은 개수 |
| POST | `/api/notifications/{id}/read` | 읽음 처리. 다른 사용자 알림은 **404**(존재 여부 비노출) |
| POST | `/api/notifications/read-all` | 내 알림 모두 읽음 |
| POST | `/api/notifications/refresh` | 내 최근 분실물 다시 매칭 → 새 후보 알림 생성 |

상태 변경도 `POST`를 사용했다. 기존 CORS 정책이 GET/POST/OPTIONS만 허용하므로, 보안 설정을 넓히지 않았다.

### 3. 사용 기술

- Spring Boot 3.5 / Spring Data JPA / MySQL (`match_notifications` 테이블, 유일 제약·인덱스)
- Spring 트랜잭션 이벤트: `@TransactionalEventListener(AFTER_COMMIT)`, 저장은 `REQUIRES_NEW`
- Java 21 가상 스레드: 여러 분실물을 병렬로 다시 매칭, 최대 2개 동시
- Spring Security OAuth2 Resource Server (JWT)
- React 19 Context (`MatchNotificationProvider`), TypeScript, Vitest + jsdom

### 4. 핵심 설계 — "알림을 언제 만들까?"

실시간 감시(스케줄러·WebSocket·푸시)를 만들지 않았다. 대신 현재 구조와 일정에서 가장 단순하고 안정적인 **두 가지 시점**에 알림을 만든다.

| 시점 | 대상 | 경찰청 호출 | 이유 |
| --- | --- | --- | --- |
| ① LOST QUEST 습득물 등록 직후 (커밋 후) | 새 습득물 ↔ 기간이 맞는 다른 사람의 진행 중 분실물 (최대 200개) | 없음 | "새 후보"가 생기는 정확한 순간. 우리 DB 데이터라 즉시 알 수 있음 |
| ② `POST /api/notifications/refresh` (로그인 시, 알림 화면 "새 매칭 확인", 분실물 등록 직후) | 내 진행 중 분실물 중 최근 30일 이내 최대 5개 | 분실물당 최대 3회 (기존 매칭과 동일) | 경찰청 데이터는 저장하지 않으므로, 사용자가 올 때 다시 조회해야 새 후보를 알 수 있음 |

선택 이유:

- 경찰청 데이터는 외부 데이터이고 영구 저장하지 않는 원칙(06단계)이 있다. 그래서 "경찰청에 새 습득물이 올라왔는지"는 **다시 조회해야만** 알 수 있다.
- 스케줄러로 모든 사용자의 분실물을 주기적으로 조회하면, 경찰청 호출량이 사용자 수에 비례해 늘고 장애 처리도 복잡해진다.
- 사용자가 실제로 앱을 쓸 때(로그인·알림 화면)만 다시 매칭하고, **같은 분실물은 10분에 한 번만** 하도록 서버에서 제한했다. 클라이언트가 아무리 자주 호출해도 경찰청 호출은 늘지 않는다.
- LOST QUEST 자체 습득물은 등록 이벤트로 즉시 알릴 수 있으므로 별도 조회가 필요 없다.

알림 기준:

| 상수 | 값 | 의미 |
| --- | --- | --- |
| `NOTIFY_MIN_SCORE` | 70 | 강한 후보만 알림. 매칭 추천의 최소 40점보다 엄격하다. 예: 분류+색상+3일 이내 = 73 |
| `NOTIFY_TOP_N` | 5 | refresh 1회에 분실물별 상위 5개 후보만 검토 (알림 폭주 방지) |
| `REFRESH_LOOKBACK_DAYS` | 30 | 이보다 오래된 분실물은 후보 기간이 끝나서 다시 매칭하지 않음 |
| `MAX_REFRESH_LOST_ITEMS` | 5 | refresh 1회에 다시 매칭할 분실물 수 |
| `app.notifications.refresh-interval` | 10분 | 분실물별 다시 매칭 최소 간격 |

### 5. 기존 매칭 시스템과 연결

점수 계산 로직은 **한 줄도 새로 만들지 않았다.**

```
MatchingService.findMatches()  ─┐
                                ├─ MatchingService.run(lostItem, limit)   ← 07단계 로직을 메서드로 분리
MatchNotificationService.refresh() ┘     · LOST QUEST 후보 + 경찰청 후보 (출처별 장애 격리)
                                         · MatchingEngine.rank (분류 35 · 지역 25 · 색상 20 · 날짜 20)

MatchNotificationService.onFoundItemRegistered()
   → MatchingService.toCandidate(foundItem) + MatchingEngine.score(target, candidate)
```

- 07단계 `findMatches`의 계산 부분을 `run()`으로 분리만 했다. 매칭 API 응답은 동일하다 (회귀 테스트로 확인).
- 습득물 등록 시 비교하는 분실물 기간(습득일 30일 전 ~ 습득일)은 매칭 API의 후보 기간(분실일 ~ +30일)을 반대 방향에서 본 것과 같다. 그래서 알림 후보는 매칭 화면에서도 같은 점수로 계산된다.
- 경찰청 장애 시: `run()`이 출처별로 격리하므로 LOST QUEST 후보 알림은 그대로 생성된다. refresh 응답 `sources`에 `POLICE: UNAVAILABLE`과 안내 문구가 표시된다.
- 알림 생성 실패(예외)는 로그만 남기고, 습득물 등록·조회·매칭 API에는 영향을 주지 않는다.

### 6. 중복 알림 방지

| 단계 | 방법 |
| --- | --- |
| DB | `UNIQUE (lost_item_id, candidate_key)` — `candidate_key`는 매칭 API와 같은 안정 ID (`LOST_QUEST:21`, `POLICE:F2026100600004521-1`) |
| 저장 | `MatchNotificationWriter.insertIfAbsent` — 존재 확인 후 저장, **알림 1건마다 별도 트랜잭션(REQUIRES_NEW)** |
| 동시 요청 | 같은 행을 동시에 넣으면 유일 제약 위반 → 호출부에서 "이미 알림 있음"으로 처리. 별도 트랜잭션이라 다른 알림이나 요청 전체가 실패하지 않음 |
| refresh 동시 호출 | 분실물별 간격 제한을 원자적으로 획득(`ConcurrentHashMap.compute`). 동시에 6번 호출해도 실제 매칭은 1번 |

프론트엔드 중복 방지에 의존하지 않는다. 같은 후보는 refresh를 몇 번 하든, 등록 이벤트와 refresh가 겹치든 한 번만 알린다.

외부 문자열 검증:

- 경찰청 관리번호는 확인된 형식(`F` + 숫자 16자리)과 순번 1~999만 저장한다. key가 ID와 정확히 일치해야 한다. 그 외(`../../admin`, key 불일치 등)는 저장하지 않는다.
- 습득물 제목은 제어문자를 제거하고 120자로 자른다. 화면 링크도 프론트에서 route 형식을 다시 검증하고, 잘못된 ID면 링크를 만들지 않는다.

### 7. 보안

- 사용자 식별은 JWT subject만 사용한다. `userId` 파라미터는 받지 않는다 (`?userId=`를 붙여도 무시되어 404).
- 알림 조회·읽음 처리 쿼리에 `user_id = 로그인 사용자` 조건이 들어 있다. 다른 사용자 알림 ID는 "없는 알림"과 똑같이 404로 응답해, ID를 바꿔 존재 여부를 알아낼 수 없다.
- 알림 수신자는 항상 분실물 작성자다 (서버가 결정). 습득자 본인의 분실물에는 알리지 않는다.
- 인증 없음·잘못된 토큰 401, 잘못된 ID(0, 문자) 400, `limit` 범위 밖 400.
- 응답·로그에 경찰청 키·URL을 포함하지 않는다.

### 8. Frontend

- `services/notificationApi.ts`: API 호출과 응답 검증, 문구 생성. 받침에 따라 "과/와"를 고른다: ‘검정 지갑’과 / ‘노트북 파우치’와.
- `context/MatchNotificationContext.tsx`: 헤더와 알림 목록이 공유하는 읽지 않은 개수.
  - 로그인하면 refresh를 1회 실행한다 (백그라운드).
  - 화면을 이동할 때마다 가벼운 `unread-count`만 다시 조회한다 (폴링·WebSocket 없음).
- `components/MatchNotificationList.tsx` (마이페이지 "알림" 탭)
  - 상태: 로딩, 빈 목록, 오류 + 다시 시도, "새 매칭 확인" 진행 중/결과 안내, 경찰청 장애 안내
  - 읽지 않은 알림: "새 알림" 배지, 강조 배경. 읽은 알림: "· 읽음"
  - 알림 클릭: 읽음 처리 → 습득물 상세 / 매칭 추천으로 이동
  - 접근성: `ul aria-label`, 링크별 고유 `aria-label`(습득물·분실물 이름 포함), `role="status"`/`role="alert"`, 장식 아이콘 `aria-hidden`
- 헤더 벨: 숫자 배지(99+), `aria-label="알림, 읽지 않은 매칭 알림 N개"`. 비로그인 시 배지 없음, 요청 없음.
- 분실물 등록 완료 시 refresh를 백그라운드로 실행한다.
- **기존 데모 알림 처리:** 반환·QR·경험치 체험(이번 범위 밖)이 만드는 브라우저 메시지는 삭제하지 않았다. "반환 체험 소식" 섹션으로 분리하고 데모임을 명시했으며, 헤더 배지에는 서버 매칭 알림만 센다. 서버 알림 조회가 실패해도 데모 메시지로 대체하지 않고 오류를 표시한다.
- my-items(내가 등록한 물품) 탭과 기능은 그대로 유지했다.

### 9. 구현 중 발생한 문제와 해결

#### 문제 1. 습득물 등록 트랜잭션 안에서 알림을 만들면 등록이 실패할 수 있음

알림 저장 중 유일 제약 위반이 나면 같은 트랜잭션의 습득물 등록까지 롤백된다.

**해결:**
- 등록 서비스는 이벤트만 발행한다. 알림은 **커밋 이후(AFTER_COMMIT)** 에 처리한다.
- 알림 1건마다 `REQUIRES_NEW` 트랜잭션으로 저장하고, 예외는 모두 잡아서 로그로만 남긴다.
- 실제 MySQL에서 습득물 등록 응답 시간은 0.51초였다 (알림 생성 포함).

#### 문제 2. 동시 요청 시 중복 알림

"없으면 저장" 확인만으로는 동시 요청 둘이 모두 "없음"을 볼 수 있다.

**해결:**
- DB 유일 제약을 최종 방어선으로 두었다. 위반은 "이미 있음"으로 처리한다.
- 8개 스레드 동시 저장 테스트에서 1건만 저장됐다.
- 실제 MySQL에 중복 행을 직접 INSERT하면 DB가 거부하는 것도 확인했다.

#### 문제 3. 읽음 시각이 응답과 DB에서 다름

첫 응답은 나노초(`…758578400Z`)였지만 DB(`DATETIME(6)`)에는 마이크로초로 저장된다. 그래서 다시 조회하면 값이 달라졌다 (테스트에서 발견).

**해결:** 서버 시각을 마이크로초로 잘라 사용해, 응답 값과 저장 값을 같게 했다.

#### 문제 4. 테스트에서 커밋 후 이벤트가 실행되지 않음

기존 통합 테스트는 `@Transactional`이라 커밋이 일어나지 않고, 그래서 AFTER_COMMIT 이벤트도 실행되지 않는다.

**해결:**
- 알림 통합 테스트는 실제로 커밋하는 비트랜잭션 테스트로 작성하고, 각 테스트 전후에 데이터를 정리했다.
- 기존 테스트는 영향 없음 (커밋이 없으니 알림도 생기지 않음).

#### 문제 5. 경찰청 외부 ID를 그대로 저장할 위험

**해결:** 관리번호 형식, 순번 범위, key-ID 일치를 검증한다. 형식이 이상한 후보는 알림을 만들지 않는다 (테스트: `../../admin`, key 불일치).

#### 문제 6. 작업 중단과 브랜치 재구성

수업 종료로 작업을 stash에 보관했다. my-items가 먼저 main에 병합된 뒤 복구하는 과정에서 `SecurityConfig`, `MyPage.tsx`, `myItemList.test.tsx`에 충돌이 났다.

**해결:**
- 세 파일 모두 "my-items 최신 코드 + 알림 추가분"으로 해결했다.
- main 대비 diff가 추가만 있음(my-items 코드 삭제·변경 없음)을 확인했다.
- my-items 테스트를 포함한 전체 테스트를 다시 실행했다.

#### 문제 7. `mvnw clean` 실패

VS Code Java 확장이 `target/*.jar` 파일을 잡고 있어 clean이 실패했다.

**해결:** 컴파일 결과 폴더(`target/classes`, `test-classes`)를 직접 지우고 처음부터 다시 컴파일해 전체 테스트를 실행했다. 실행 검증은 `spring-boot:run`으로 했다.

### 11. 발표에서 강조할 포인트

1. **매칭 엔진 재사용.** 알림용 점수 로직이 없다. 추천 화면과 알림이 항상 같은 점수를 보여 준다.
2. **스케줄러 없이 "새 후보"를 알리는 구조.** 우리 데이터는 등록 이벤트로 즉시 알리고, 저장하지 않는 경찰청 데이터는 사용자가 올 때 다시 조회한다. 서버의 간격 제한으로 외부 API 호출량도 통제한다.
3. **중복 알림은 DB가 막는다.** 유일 제약 + 알림별 트랜잭션. 동시 요청·반복 refresh에도 1건.
4. **장애 격리.** 경찰청이 멈춰도 LOST QUEST 알림은 동작한다. 알림이 실패해도 등록은 성공한다.
5. **보안.** JWT 사용자만, 타인 알림 ID는 404, 외부 ID 형식 검증.

### 13. 현재 제한사항 및 추후 개선

- **실시간 아님:** 다른 사용자가 습득물을 등록해도 화면을 이동하거나 새로고침해야 배지가 갱신된다. → 개선: SSE/WebSocket 또는 Web Push(FCM)
- **경찰청 새 습득물:** 사용자가 로그인하거나 "새 매칭 확인"을 눌러야 발견된다. 앱을 열지 않으면 알 수 없다. → 개선: 스케줄러(예: 하루 몇 회, 최근 분실물만)와 경찰청 호출량 예산
- **간격 제한은 서버 메모리에 저장:** 재시작하면 초기화되고, 서버가 여러 대면 각자 관리한다. → 개선: DB 컬럼 또는 Redis
- **첫 refresh:** 등록 직후의 기존 상위 후보도 "새 알림"으로 표시된다 (최대 5건). 매칭 화면을 먼저 본 경우에도 알림이 생긴다.
- **점수 스냅샷:** 알림의 점수·습득물 제목은 생성 시점 값이다 (이후 바뀌어도 갱신하지 않음).
- **분실물 5개 제한:** refresh는 최근 30일 안의 진행 중 분실물 최대 5개만 다시 매칭한다. 상위 5개 밖 후보는 알리지 않는다.
- 알림 삭제, 알림 설정(끄기·기준 점수 변경), 이메일·SMS는 범위 밖이다.
- 반환·QR·경험치 데모 소식은 아직 브라우저 데모 데이터다 (서버화는 다음 단계).
