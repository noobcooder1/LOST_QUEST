# LOST QUEST 발표자료 개발 기록

## 07. 분실물–습득물 매칭 추천 v1

### 1. 구현 목적

지금까지 "AI 매칭" 화면은 브라우저 가상 데이터만 비교하는 시뮬레이션이었다.

이번 단계에서는 사용자가 실제로 등록한 분실물을 기준으로

React
→ LOST QUEST Spring Boot (`GET /api/lost-items/{id}/matches`)
→ ① LOST QUEST 습득물(MySQL) + ② 경찰청 습득물(OpenAPI 실시간)
→ 규칙 기반 메타데이터 점수 계산
→ 매칭도 순 추천 목록 + 점수 근거
→ React 매칭 화면

흐름으로 **실제 데이터 기반 습득물 추천**을 구현하였다.

- 점수는 분류·지역·색상·날짜 4가지 조건의 일치 여부로만 계산한다 (총 100점).
- 이미지 비교·AI 판단은 하지 않는다. 화면에도 "AI", "정확도", "확률" 표현을 쓰지 않고 **"매칭도 N점"** 으로 표시한다.
- 추천은 참고용이며 소유권 확인이나 매칭 확정이 아니다.

### 2. API

```
GET /api/lost-items/{id}/matches?limit=10
Authorization: Bearer <access token>
```

| 항목 | 내용 |
| --- | --- |
| 인증 | 필수 (JWT). 사용자는 JWT subject에서만 결정하며 `userId` 파라미터는 받지 않는다 |
| 권한 | **분실물 작성자 본인만** 조회 가능. 다른 사용자 403 `FORBIDDEN` |
| `id` | 양의 정수, 없는 분실물 404 |
| `limit` | 1~20, 기본 10. 범위 밖 400 `VALIDATION_ERROR` |
| 정렬 | 매칭도 내림차순 → 분실일과의 날짜 차이 오름차순(미상은 뒤) → 안정 ID 오름차순 |
| 최소 점수 | 40점 미만은 추천하지 않음 |

본인만 볼 수 있게 한 이유: 추천 결과는 개인의 분실 정보에 대한 결과이고, 요청마다 경찰청 API를 호출하므로 누구나 임의의 분실물에 대해 호출하지 못하게 한다.

응답 예시 (실제 검증 응답 축약):

```json
{
  "lostItem": { "id": 45, "title": "검은색 반지갑", "category": "지갑", "color": "검정", "region": "서울", "lostDate": "2026-10-01" },
  "maxScore": 100, "minScore": 40, "limit": 10,
  "matches": [
    {
      "id": "POLICE:F2026100600004521-1", "source": "POLICE",
      "foundItemId": null, "atcId": "F2026100600004521", "fdSn": 1,
      "title": "검정 카드지갑", "category": "지갑", "color": "블랙(검정)", "foundDate": "2026-10-02",
      "region": "서울특별시", "location": null, "storagePlace": "월계지구대", "imageUrl": "https://minwon24.police.go.kr/...",
      "score": 98, "maxScore": 100,
      "scoreBreakdown": [
        { "key": "category", "points": 35, "maxPoints": 35, "result": "MATCH",   "note": null },
        { "key": "region",   "points": 25, "maxPoints": 25, "result": "MATCH",   "note": null },
        { "key": "color",    "points": 20, "maxPoints": 20, "result": "MATCH",   "note": null },
        { "key": "date",     "points": 18, "maxPoints": 20, "result": "PARTIAL", "note": null }
      ],
      "reasons": ["같은 분류(지갑)", "같은 지역(서울특별시)", "같은 색상(블랙(검정))", "분실 1일 후 습득"]
    }
  ],
  "sources": [
    { "source": "LOST_QUEST", "status": "OK", "candidateCount": 2,  "message": null },
    { "source": "POLICE",     "status": "OK", "candidateCount": 89, "message": null }
  ]
}
```

- `id`는 출처별로 구분되는 안정 ID: `LOST_QUEST:{습득물 id}` / `POLICE:{atcId}-{fdSn}`
- `score`는 항상 `scoreBreakdown.points`의 합과 같고, `reasons`는 **점수를 받은 항목만** 순서대로 담는다.
- `result`: `MATCH`(만점) / `PARTIAL`(일부 점수) / `MISMATCH`(비교했지만 불일치, 0점) / `UNKNOWN`(정보가 없어 비교 불가, 0점 + `note`)
- `sources[].status`: `OK` / `PARTIAL`(일부 조회 실패) / `UNAVAILABLE`(조회 실패) / `SKIPPED`(검색하지 않음). `message`는 사용자용 문구이며 키·URL을 포함하지 않는다.
- 이미지 점수(`imageScore`)는 계산하지 않으므로 응답에 넣지 않았다 (0점짜리 가짜 항목을 만들지 않음).

### 3. 점수 규칙

| 항목 | 만점 | 규칙 |
| --- | --- | --- |
| 분류 | 35 | 이름이 같으면 35. LOST QUEST 분류 ↔ 경찰청 **대분류 이름**(예: "지갑 > 남성용 지갑"의 "지갑") |
| 지역 | 25 | 같은 지역이면 25. 경찰청 습득물은 지역 정보가 없으면 `UNKNOWN` |
| 색상 | 20 | 정규화한 색상 이름이 같으면 20 |
| 날짜 | 20 | 분실일 → 습득일: 당일 20, 1~3일 18, 4~7일 12, 8~14일 6, 15일 이상 0, **분실일보다 먼저 습득 0** |

- 정보가 없거나 해석할 수 없는 값(빈 색상, 날짜 없음 등)은 해당 항목만 `UNKNOWN` 0점이며, 전체 추천이 실패하지 않는다.
- 점수 정책 값은 각 기준 클래스의 상수(`CategoryCriterion.MAX_POINTS` 등)와 `MatchingService.MIN_SCORE`, `DateCriterion`의 날짜 구간 상수로 관리한다.

#### 이름 정규화 (매핑 테이블 없이 규칙만 사용)

실제 데이터 값을 먼저 조사한 뒤 규칙을 정했다.

- 개발 DB 실제 값: 분류 지갑·기타·가방·액세서리·전자기기, 색상 검정·파랑·갈색·빨강·흰색·초록·회색, 지역 서울·부산·인천·대전·경기·제주
- 경찰청 실제 공통코드: 색상 `블랙(검정)`, `브라운(갈)`, `화이트(흰)`, `그레이(회)` 형식 49개 그룹, 대분류 21개, 시·도 20개

| 규칙 | 예 |
| --- | --- |
| 공통: 공백 제거, 영문 소문자화 | "검 정" = "검정" |
| 색상: 끝의 "색" 제거, 경찰청 이름은 괄호 앞·괄호 안을 각각 비교 | 검정·검정색·블랙 = `블랙(검정)`, 갈색 = `브라운(갈)`, 흰색 = `화이트(흰)`, 회색 = `그레이(회)` |
| 지역: 경찰청 공식 이름이 LOST QUEST 이름을 포함하거나, 4글자 "…도"의 표준 약칭(1·3번째 글자)과 같음 | 서울 = 서울특별시, 경기 = 경기도, 충북 = 충청북도, 전남 = 전라남도·전남광주통합특별시, 광주 = 광주광역시·전남광주통합특별시 |

LOST QUEST 17개 지역 모두가 실제 경찰청 시·도 이름에 이 규칙으로 연결되는 것을 테스트로 확인하였다.

임의로 맞추지 않은 것:

- LOST QUEST "액세서리" ↔ 경찰청 "귀금속", "기타" ↔ "기타물품", "전자기기" ↔ "휴대폰"은 이름이 달라 **일치로 처리하지 않는다** (근거 없는 매핑 테이블을 만들지 않음).
- `블루(어두운파랑)`의 "어두운파랑"은 "파랑"과 다른 이름이므로 불일치. 유사 색상 부분 점수는 없다.

### 4. 후보 수집

전체 DB·전체 경찰청 데이터를 읽지 않고 **조건으로 먼저 좁힌 뒤** 점수를 계산한다.

#### LOST QUEST 습득물

```java
foundItemRepository.findTop200ByStatusAndFoundDateBetweenAndUser_IdNotOrderByFoundDateAscIdAsc(
        STORED, lostDate, lostDate + 30일, 요청자 id)
```

- 보관 중(`STORED`)인 습득물만, 습득일이 분실일 ~ +30일, 최대 200건
- 요청자 본인이 등록한 습득물은 제외
- 분실일보다 먼저 습득된 물품은 같은 물건일 수 없으므로 후보에서 제외 (점수 규칙상으로도 0점)

#### 경찰청 습득물 (`PoliceCandidateCollector`)

기존 `PoliceItemService.listFound`(키 처리·입력 검증·XML 정규화·이미지 정책)를 그대로 재사용한다. Backend 내부 HTTP 호출이나 프론트엔드 직접 호출은 없다.

| 조회 | 조건 |
| --- | --- |
| 지역별 (최대 2회) | 시·도 코드(분실 지역 규칙으로 찾은 코드) + 대분류 코드 |
| 전국 (1회) | 대분류 코드만 |

- 기간: 분실일 ~ min(분실일 + 14일, 오늘)
- 대분류 코드는 실시간 공통코드에서 **이름이 같은 대분류**로 찾고, 없으면 분류 조건 없이 조회한다.
- 한 조회당 1페이지 50건, 최대 3회를 **병렬**(가상 스레드)로 호출한다.
- **색상 조건은 보내지 않는다.** 경찰청 API는 색상 코드를 한 번에 하나만 받아 색상 그룹(예: 그레이 15개 코드)마다 호출이 늘어나기 때문에, 색상은 가져온 뒤 비교한다.
- 경찰청 습득물 목록에는 지역 필드가 없다. 지역 조건으로 조회된 물품에만 그 시·도 이름을 지역으로 기록하고, 전국 조회로만 나온 물품은 지역 `UNKNOWN`이다 (지역 일치로 표시하지 않음). 같은 물품이 두 조회에 모두 나오면 지역이 확인된 쪽을 남긴다.
- 상세 링크에 필요한 `atcId`·`fdSn`이 없는 항목은 ID를 만들어내지 않고 제외한다.

#### 출처 독립성

- 경찰청 공통코드 실패 → 경찰청 `UNAVAILABLE`, 목록 호출 없음
- 경찰청 일부 조회 실패 → `PARTIAL`, 성공한 조회 결과만 사용
- 경찰청 전체 실패 → `UNAVAILABLE`, **LOST QUEST 추천은 그대로 반환** (200)
- LOST QUEST DB 후보 조회 실패 → LOST QUEST `UNAVAILABLE`, 경찰청 추천은 그대로 반환
- DB 조회는 각 repository 트랜잭션에서 짧게 끝나고, 경찰청 호출 중에는 DB 연결을 잡고 있지 않다 (`MatchingService`는 트랜잭션 없음, 작성자 확인은 `join fetch` 쿼리).

### 5. Backend 구조

```
LostItemController   GET /api/lost-items/{id}/matches  (@Positive id, @Min(1) @Max(20) limit, JWT)
        ↓
MatchingService      작성자 확인(403/404) → 후보 수집 → 점수 → 정렬·limit → ItemMatchResponse
   ↓                    ↓                              ↓
FoundItemRepository  PoliceCandidateCollector       MatchingEngine
(기간·상태·200건)     → PoliceItemService.listFound    → MatchCriterion (Spring bean, @Order)
                     → PoliceCodeService.codes()        CategoryCriterion 35
                                                        RegionCriterion   25
                                                        ColorCriterion    20
                                                        DateCriterion     20
```

- `service/matching` 패키지: `MatchCriterion`(점수 항목 인터페이스), `CriterionResult`(점수·만점·결과·이유, "점수가 있을 때만 이유" 불변식 검증), `MatchingEngine`, `MatchText`(정규화 규칙), `MatchCandidate`/`MatchTarget`/`SourceResult`
- 기존 3계층, DTO(`ItemMatchResponse`), `GlobalExceptionHandler`(403/404/400), `SecurityConfig`(해당 경로 `authenticated()` 1줄 추가) 구조를 유지하였다.
- 새 점수 항목(예: 이미지 유사도)은 `MatchCriterion` 구현 클래스를 하나 추가하면 엔진·응답 구조 변경 없이 `scoreBreakdown`에 포함된다. (단, 만점 배분 100점 재조정 필요)

### 6. Frontend 연동

- `services/matchingApi.ts`: `getItemMatches(serverId)` — sessionStorage의 Access Token을 `Authorization` 헤더로 보냄 (URL에 토큰·userId 없음). 응답 검증: 점수 = breakdown 합계, 출처별 상세 route id(`api-found-{id}` / `police-found-{atcId}-{fdSn}`) 생성 가능 여부, 이미지 URL 허용 목록(LOST QUEST `/api/images/…`, 경찰청 첨부 이미지 형식)
- `pages/MatchingPage.tsx`: 기존 매칭 화면 레이아웃·CSS를 재사용하고 데이터 출처만 실제 API로 교체
  - 내 분실물 선택: `GET /api/lost-items` 중 `ownerId === 로그인 사용자` 이고 진행 중인 것
  - 카드: 사진(`ItemImage`: 실제 사진 → 종류별 기본 이미지 → 아이콘), 제목, 출처 배지, **매칭도 N점**, 점수를 받은 조건, 항목별 점수(정보 없음 표시), 지역·보관 장소, 습득일, 상세 링크
  - 정렬: 매칭도순(서버 순서) / 최신 습득순
  - 상태: 로그인 필요, 로딩, 내 분실물 없음, 결과, 결과 없음, 경찰청만 실패(LOST QUEST 결과 + 안내), 일부 실패, 전체 실패, 403(남의 분실물), 404, 기타 오류 + 다시 시도
  - **가상 데이터로 대체하지 않는다** (silent demo fallback 없음)
- 진입점: 상세 화면(내 분실물일 때만 "매칭 추천 보기"), 분실물 등록 완료 화면, 상단·모바일 메뉴 "매칭 추천"(기존 "AI 매칭" 표기 변경), 홈 링크 문구
- 기존 데모 매칭 함수(`services/matching.ts`)는 데모 반환 흐름 테스트에서 쓰이므로 남겨 두었다.

### 7. 보안

- 사용자 식별은 JWT subject만 사용, 클라이언트 `userId`는 무시 (`?userId=` 붙여도 403 확인)
- 작성자 확인은 서버에서 수행 (프론트의 내 분실물 필터는 표시용)
- 경찰청 인증키는 기존과 같이 Backend에서만 사용, 응답·로그·문서에 키나 키가 포함된 URL 없음 (실제 응답에서 `serviceKey`·`apis.data.go.kr` 미포함 확인)
- 브라우저는 경찰청 API를 호출하지 않음 (실제 브라우저 요청 host: 프론트엔드, LOST QUEST API, 허용된 경찰청 **이미지** URL만)
- 경찰청 오류 메시지는 기존 `ExternalApiException.Kind`의 사용자용 문구만 전달

### 8. 성능

| 항목 | 값 |
| --- | --- |
| DB 후보 | 최대 200건 (상태·기간 조건) |
| 경찰청 호출 | 최대 3회 × 50건, 병렬. 색상 fan-out 없음 |
| 점수 계산 | 후보 최대 약 350건 × 4개 항목, 메모리 계산 |
| 실제 응답 시간 | 첫 요청 4.8초(공통코드 로딩 포함), 반복 1.4초 (서울 지갑, 실제 경찰청 API) |

- 결과 캐시는 두지 않았다 (경찰청 데이터는 계속 바뀌고, 저장하지 않는다는 기존 원칙 유지).
- 프론트엔드 요청 제한 시간은 45초 (경찰청 응답 지연 대비).

### 10. 한계

- **이미지 비교 없음**: 사진이 비슷한지는 점수에 반영되지 않는다.
- **경찰청 지역**: 습득물 목록에 지역 필드가 없어 지역 조회 결과에만 지역 점수를 줄 수 있다. 시·군·구 단위는 경찰청 API에서 동작하지 않아 시·도 단위만 비교한다.
- **경찰청 표본**: 조회당 첫 페이지 50건만 사용한다. 서울처럼 건수가 많은 지역은 기간 내 모든 습득물을 비교하지 못한다.
- **분류 이름 차이**: 액세서리↔귀금속, 기타↔기타물품, 전자기기↔휴대폰 등은 일치로 처리하지 않는다. 휴대폰을 "전자기기"로 등록하면 경찰청 "휴대폰" 습득물은 분류 점수를 받지 못하고, 경찰청 조회도 "전자기기" 대분류로만 한다.
- **색상 자유 입력**: LOST QUEST 색상은 자유 입력이라 "검은색"처럼 다른 표현은 "검정"과 일치하지 않는다. 유사 색상 부분 점수도 없다.
- **분실일 이전 습득**: 날짜를 잘못 기억한 경우를 고려하지 않고 후보에서 제외한다.
- 물품명·설명 텍스트는 비교하지 않는다.
- 추천은 요청 시 계산하며 알림·저장·매칭 확정 기능은 없다.
