# LOST QUEST 발표자료 개발 기록

## 05. 이미지 업로드 및 저장

### 구현 목적

기존 등록 화면에서 사용자가 선택한 사진은 브라우저 미리보기로만 쓰였고 서버에는 전송되지 않았다.
그래서 등록된 물품은 목록과 상세 화면에서 항상 종류별 기본 이미지로만 표시되었다.

이번 단계에서는 사용자가 등록한 실제 사진을

React
→ Spring Boot
→ 이미지 저장소
→ MySQL

까지 연결하고, 목록과 상세 화면에서 다시 표시되도록 구현하였다.

---

### 주요 기능

- 분실물/습득물 등록 시 사진 1장 선택 업로드 (선택 사항)
- JPEG / PNG / WebP만 허용, 최대 10MB
- Content-Type과 파일 시그니처(매직 넘버)를 함께 검증
- 서버가 UUID 기반 저장 파일명 생성 (원본 파일명 미사용)
- 개발 환경 로컬 저장소(`.local/uploads`, Git 제외, 설정으로 변경 가능)
- DB에는 서버 기준 상대 경로(`/api/images/{uuid}.jpg`)만 저장
- 사진 조회 API `GET /api/images/{filename}` (공개)
- 목록/상세 응답의 `imageUrl`로 실제 사진 표시
- 사진이 없는 기존 데이터는 종류별 기본 이미지 유지
- DB 등록 실패 시 저장한 사진 파일 자동 삭제
- 기존 JSON 등록 API 호환 유지

이번 단계에서 **AWS S3 연동, AI 이미지 분석, 사진 수정/삭제는 구현하지 않았다.**

### 이미지 업로드 흐름

사진이 있는 등록:

React 등록 화면
→ 사진 선택 (FileReader로 미리보기, 실제 File 객체는 별도 보관)
→ POST /api/lost-items (multipart/form-data)
  - `item` 파트: 기존과 같은 등록 JSON
  - `image` 파트: 사진 파일
  - `Authorization: Bearer {token}`
→ Spring Security JWT 검증
→ Controller (`@Valid @RequestPart("item")`로 입력 검증)
→ Service
  1. JWT 사용자 ID로 DB 사용자 확인
  2. ImageService: 크기·형식·시그니처 검증 후 UUID 파일명으로 저장
  3. LostItem 저장 (`image_url = /api/images/{uuid}.jpg`)
→ 201 Created + imageUrl 포함 DTO

사진이 없는 등록:

기존과 같은 JSON 요청(`application/json`)을 그대로 사용한다.

조회:

GET /api/lost-items
→ `imageUrl: "/api/images/{uuid}.jpg"`
→ 프론트엔드가 API 주소와 결합
→ `<img src="http://localhost:8080/api/images/{uuid}.jpg">`
→ GET /api/images/{uuid}.jpg
→ 사진 파일 응답

### 저장 구조

| 구분 | 내용 |
| --- | --- |
| 저장 위치 | `backend/.local/uploads/` (설정 `app.image-storage.local-dir` / 환경변수 `IMAGE_STORAGE_LOCAL_DIR`) |
| 파일명 | `{UUID}.{jpg\|png\|webp}` (서버 생성, 확장자는 실제 파일 시그니처 기준) |
| DB `image_url` | `/api/images/{UUID}.jpg` (서버 기준 상대 경로) |
| API 응답 `imageUrl` | DB 값과 동일 |
| 화면 표시 | `VITE_API_BASE_URL` + `imageUrl` |

저장 로직은 계층을 나누었다.

- `ImageStorage` 인터페이스: 저장 / 조회 / 삭제
- `LocalImageStorage`: 개발용 로컬 디스크 구현
- `ImageService`: 검증, 파일명 생성, 트랜잭션 연동

향후 AWS S3를 도입할 때는 `ImageStorage`의 S3 구현만 추가하면 되고,
검증 로직과 Controller, 등록 Service는 바꿀 필요가 없도록 설계하였다.

DB에 `localhost` 주소나 `D:\...` 같은 실제 경로를 저장하지 않기 때문에
서버 주소나 저장 위치가 바뀌어도 기존 데이터를 수정할 필요가 없다.

### 보안 검증

#### 1. 파일 형식 검증

클라이언트가 보내는 Content-Type은 조작할 수 있으므로 신뢰하지 않는다.
실제 파일 앞부분의 시그니처를 확인하고, 선언된 Content-Type과도 일치해야 저장한다.

| 형식 | 시그니처 |
| --- | --- |
| JPEG | `FF D8 FF` |
| PNG | `89 50 4E 47 0D 0A 1A 0A` |
| WebP | `RIFF` + 4바이트 + `WEBP` |

거부 확인 사례:

- SVG (스크립트 포함 가능)
- `image/png`로 위장한 SVG
- `image/jpeg`로 위장한 HTML
- GIF, 텍스트 파일, 빈 파일
- 실제 JPEG를 `image/png`로 선언한 경우

#### 2. 경로 조작(Path Traversal) 차단

- 원본 파일명(`../../evil.jpg` 등)은 저장에 사용하지 않고 UUID로 새 이름 생성
- 조회 API는 `UUID.jpg|png|webp` 형식 이름만 허용
- 저장소에서도 최종 경로가 저장 디렉터리 바로 아래인지 다시 확인
- `application.yml`, `../pom.xml` 등 조회 시도는 404/400

#### 3. 권한

- 사진 포함 등록도 기존과 같이 JWT 로그인 필수 (비로그인 401)
- 작성자는 JWT 사용자, 상태는 서버가 결정
- 클라이언트가 `imageUrl`을 JSON에 넣어도 무시 (서버가 저장한 사진 경로만 사용)
- 인증 실패·입력 오류는 **사진을 저장하기 전에** 거부

#### 4. 응답 보안 헤더

사진 응답에는 다음 헤더를 붙였다.

- `X-Content-Type-Options: nosniff`
- `Content-Security-Policy: default-src 'none'; sandbox`
- 정확한 이미지 Content-Type

#### 5. 프론트엔드 방어

서버 응답의 `imageUrl`이 `/api/images/{UUID}.{jpg|png|webp}` 형식이 아니면
(외부 URL, data URL, 예상하지 못한 경로 등) 사용하지 않고 기본 이미지를 표시한다.

### 핵심 구현 및 설계

#### 1. 기존 JSON API 호환

같은 등록 주소에 `multipart/form-data` 전용 처리 메서드를 추가하였다.

- `Content-Type: application/json` → 기존 JSON 등록 (변경 없음)
- `Content-Type: multipart/form-data` → `item` + 선택 `image`

기존 클라이언트와 기존 테스트는 수정 없이 그대로 동작한다.
별도 업로드 API를 먼저 호출하고 결과 key를 등록 요청에 넣는 방식은
다른 사용자의 key를 재사용하거나 등록되지 않은 파일이 남을 수 있어 선택하지 않았다.

#### 2. DB 등록 실패 시 파일 정리

사진을 먼저 저장한 뒤 DB INSERT가 실패하면 연결된 물품이 없는 파일이 남을 수 있다.

`ImageService`는 반드시 등록 트랜잭션 안에서만 호출되도록 하고
(`Propagation.MANDATORY`), 파일 저장 직후 트랜잭션 완료 콜백을 등록한다.

트랜잭션이 커밋되지 않으면(롤백) 저장한 파일을 즉시 삭제한다.

또한 파일은 임시 이름으로 쓴 뒤 원자적으로 이동(`ATOMIC_MOVE`)하여
중간에 실패해도 반쯤 쓰인 파일이 실제 이름으로 남지 않도록 하였다.

#### 3. 등록 화면 UX 유지

- 사진 선택 시 기존처럼 즉시 미리보기
- 미리보기용 data URL과 별도로 실제 File 객체를 보관하여 업로드
- 샘플 이미지를 고르면 사진 없이 등록 (종류별 기본 이미지)
- 클라이언트에서도 형식과 10MB 제한을 먼저 확인
- 기존 "등록 중…" 중복 제출 방지와 오류 표시 유지

### 문제와 해결

#### 문제 1. 큰 파일 업로드 시 JSON 오류 대신 연결이 끊길 수 있음

Spring Boot의 기본 multipart 제한은 1MB이고,
Tomcat은 제한을 넘는 요청 본문을 끝까지 읽지 않으면 연결을 끊을 수 있다.
이 경우 사용자는 "10MB 초과" 안내 대신 네트워크 오류를 보게 된다.

#### 해결

- multipart 제한을 파일 10MB / 요청 11MB로 설정
- Tomcat `max-swallow-size`를 20MB로 설정해 초과 요청도 응답을 받을 수 있게 함
- `MaxUploadSizeExceededException`을 기존 `ApiError` 형식의 `413 IMAGE_TOO_LARGE`로 변환

실제 HTTP로 10MB를 넘는 파일을 전송해 JSON 413 응답을 받는 것을 확인하였다.

---

#### 문제 2. MockMvc 테스트는 서블릿 업로드 크기 제한을 거치지 않음

MockMvc의 multipart 요청은 실제 서블릿 multipart 파싱을 거치지 않아
설정 파일의 크기 제한이 테스트에서 동작하지 않는다.

#### 해결

`ImageService`에서도 10MB를 직접 검사하도록 하여 설정과 무관하게 제한되도록 하였고,
자동 테스트(서비스 검사)와 실제 HTTP 검증(서블릿 제한)으로 두 경로를 모두 확인하였다.

---

#### 문제 3. 롤백 시 파일 삭제를 테스트로 확인하기 어려움

기존 테스트는 클래스 전체가 테스트 트랜잭션 안에서 실행되어
테스트가 끝날 때까지 실제 커밋/롤백이 일어나지 않는다.

#### 해결

이미지 테스트 클래스는 테스트 트랜잭션을 사용하지 않고
각 테스트 후 데이터와 파일을 직접 정리하도록 작성하였다.
`TransactionTemplate`으로 롤백/커밋을 발생시켜 파일이 삭제/유지되는 것을 확인하였다.

---

#### 문제 4. 상세 화면 사진 표시를 자동 테스트하기 어려움

프론트엔드에는 DOM 테스트 환경이 없고, 상세 화면은 서버 데이터를 렌더링 후에 불러온다.

#### 해결

새 테스트 라이브러리를 추가하지 않고, 상세 화면의 사진 영역을 작은 `ItemPhoto` 컴포넌트로 분리하였다.
목록 카드와 상세 사진을 `react-dom/server` 정적 렌더링으로 검증하였다.

- 전체 테스트 55/55 통과 (기존 42 + 신규 13)
- `mvnw clean test`, `mvnw clean package` BUILD SUCCESS

신규 `ItemImageUploadTest` 검증 항목:

- 이미지 포함 분실물(JPEG) / 습득물(PNG) 등록 성공, WebP 허용
- 응답 imageUrl 형식과 DB `image_url` 일치, 실제 파일 저장 확인
- 이미지 조회: 원본 바이트, Content-Type, 보안 헤더
- 목록/상세 응답의 imageUrl, 사진 없는 항목은 null
- 기존 JSON 등록 정상, 파일 미생성
- imageUrl/userId/status 조작 무시, `../../evil.jpg` 파일명 무력화
- SVG/HTML/GIF/텍스트/위장/빈 파일 → 400 INVALID_IMAGE
- 10MB 초과 → 413, 정확히 10MB → 허용
- 비로그인·잘못된 토큰 → 401, 파일 미생성
- DB에 없는 사용자·잘못된 입력 → 사진 저장 전 거부
- 트랜잭션 롤백 시 파일 삭제, 커밋 시 유지
- 없는 이미지 404, 경로 조작 시도 404/400

#### Frontend

- Vitest 86/86 통과 (기존 62 + 신규 24)
- TypeScript 검사 및 `npm run build` 성공

신규 검증 항목:

- 선택한 사진이 multipart `image` 파트로, 등록 정보가 `item` JSON 파트로 전송됨
- Bearer 토큰 포함, Content-Type은 브라우저가 boundary와 함께 설정
- 사진이 없으면 기존 JSON 요청 유지
- 서버 imageUrl → API 주소와 결합된 Item.image 변환
- 허용되지 않은 imageUrl(외부 URL, data URL, 경로 조작 등) 무시
- 목록 카드와 상세 사진에서 실제 이미지 표시
- imageUrl이 NULL이면 종류별 기본 이미지

#### 실제 MySQL / HTTP 통합 검증

실제 Spring Boot 서버와 로컬 MySQL에서 Pillow로 만든 실제 JPEG/PNG/WebP 파일로 확인하였다.

- 등록 → `image_url`에 `/api/images/{uuid}.*` 저장, 조회한 파일이 원본과 동일
- 사진 없는 multipart 등록과 기존 JSON 등록 → `image_url` NULL
- SVG, 위장 SVG, 위장 HTML, GIF → 400
- 10MB 초과 → 413 JSON 응답 (연결 끊김 없음)
- 토큰 없음 → 401
- 거부된 요청 후 저장 폴더에 불필요한 파일이 남지 않음
- `.local/uploads`가 Git 변경 목록에 나타나지 않음

#### 브라우저 검증

로그인
→ 등록 화면에서 사진 선택 (미리보기 유지)
→ 등록 완료 화면에 서버 사진 표시
→ 상세 화면 사진 표시
→ 검색 목록 카드 사진 표시

사진이 없는 서버 물품과 seed 데모 물품은 기존 기본 이미지로 표시되는 것도 확인하였다.
10MB 초과 파일과 SVG 파일은 등록 화면에서 선택 단계부터 안내된다.

### 현재 제한사항

- 사진은 서버를 실행한 PC의 로컬 디스크에만 저장된다. 팀원 간 공유·백업이 되지 않으며 S3 연동은 다음 단계이다.
- 사진의 EXIF 메타데이터(촬영 위치 GPS 등)를 제거하지 않는다. 습득 장소 사진에 개인 위치 정보가 포함될 수 있어 실제 공개 전에 재인코딩 또는 메타데이터 제거가 필요하다.
- (추가 수정) 업로드 시 실제 디코드 검증을 추가했다. signature만 있는 파일·잘린/손상된 이미지는 400으로 거부하고, 해상도 상한(한 변 16,384px, 5천만 화소, WebP 4096×4096)과 축소 디코드·동시 디코드 2개 제한으로 메모리 사용을 제한한다. 단, lossy WebP 내부 압축 데이터의 무작위 손상은 형식 특성상 검출하지 못하며, 이 수정 이전에 저장된 파일은 다시 검사하지 않는다.
- 사진 URL은 추측하기 어렵지만 공개 조회이다.
- 서버 프로세스가 파일 저장과 DB 커밋 사이에 강제 종료되면 파일이 남을 수 있다. (정기 정리 작업은 미구현)
- 수정/삭제 API가 없어 등록한 사진을 바꾸거나 지울 수 없다.
- `%2F`처럼 인코딩된 슬래시가 포함된 사진 주소는 Tomcat이 먼저 거부하여 `ApiError`가 아닌 기본 400 페이지가 반환된다.
- 프론트엔드에서 `VITE_API_BASE_URL`이 설정되지 않으면 서버 사진 대신 기본 이미지가 표시된다.

### 발표에서 강조할 점

사진 미리보기에서 끝나지 않고

React
→ Spring Boot
→ 이미지 저장소

까지 실제 사진이 저장되고 다시 표시되는 흐름을 완성하였다.

단순 업로드가 아니라 다음과 같은 **파일 업로드 보안**을 함께 설계하였다.

- Content-Type을 믿지 않고 파일 시그니처 검증
- 원본 파일명 대신 UUID 사용으로 경로 조작 차단
- 실제 경로가 아닌 상대 경로만 DB와 API에 노출
- DB 실패 시 파일 자동 정리

또한 저장소를 인터페이스로 분리하여 로컬 저장소에서 AWS S3로 확장할 수 있는 구조를 만들었다.

### 발표 화면 후보

- 등록 화면에서 사진 선택 후 미리보기
- 등록 완료 화면의 서버 사진
- 검색 목록 카드와 상세 화면의 실제 사진
- DBeaver: `SELECT id, title, image_url FROM lost_items ORDER BY id DESC;` (상대 경로 저장)
- `backend/.local/uploads` 폴더의 UUID 파일명
- SVG/위장 파일 업로드 시 `400 INVALID_IMAGE` 응답
- 10MB 초과 업로드 시 `413 IMAGE_TOO_LARGE` 응답
- Backend 55개 / Frontend 86개 테스트 통과 화면
