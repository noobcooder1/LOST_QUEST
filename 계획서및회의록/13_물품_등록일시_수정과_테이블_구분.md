# 물품 등록일시 수정과 분실물·습득물 테이블 구분

확인일: 2026-10-10 / 사이트 표시 기준: 한국 시간(Asia/Seoul, UTC+09:00)

## 1. 원인과 실제 등록 시각

그림리퍼 피규어(`found_items.id = 2`)의 실제 저장값과 API 응답을 확인했다.

| 구분 | 값 | 의미 |
| --- | --- | --- |
| DB `created_at` | `2026-10-10 11:27:53.949063` | UTC 기준 실제 글 등록 시각 |
| API `createdAt` | `2026-10-10T11:27:53.949063Z` | 같은 시각을 시간대가 명시된 문자열로 전달 |
| 한국 시간 | `2026-10-10 20:27:53.949063` | UTC 시각에 한국 시간대 적용 |
| DB `found_date` | `2026-09-16` | 물건을 주운 날짜로 입력·저장된 값 |

DB 시각은 임의로 생성한 값이 아니다. `BaseEntity`가 저장 직전에 `Instant.now()`로 실제 시각을 생성하고, Hibernate와 MySQL 연결은 UTC를 사용한다. `DATETIME(6)` 값 자체에는 시간대 표기가 없어서 DBeaver에서 한국 시간으로 오인하기 쉬웠다. MySQL의 현재 `NOW()`가 한국 시간이어도 이미 저장된 UTC `DATETIME` 값이 자동으로 바뀌지는 않는다.

화면 문제는 두 가지였다. 프론트엔드가 API의 `createdAt`을 화면 모델로 옮기지 않아 등록 시각을 표시하지 않았고, 등록 폼의 분실·습득 날짜 기본값이 `2026-09-16`으로 고정되어 있었다. 기존 상세 화면의 ‘습득 날짜’는 글 등록 날짜가 아니었다.

## 2. 적용한 수정

- 화면 모델에 서버의 `createdAt`을 보존한다. 사용자가 입력하는 사건 날짜와 별도 값이다.
- 상세 페이지에 ‘글 등록일시’를 추가하고, 목록 카드·내 물품 목록·등록 완료 화면에서도 한국 시간으로 표시한다. 초 단위까지 표시하며 한국 시간임을 명시한다.
- 등록 폼의 기본 날짜와 미래 날짜 판단을 한국 기준 오늘로 계산한다. 사용자는 실제 분실·습득한 과거 날짜를 선택할 수 있다.
- 백엔드 `@PastOrPresent` 검증도 한국 기준 달력을 사용한다. UTC 서버에서 한국 자정 직후의 오늘 날짜가 미래 날짜로 거절되는 일을 방지한다.
- 등록 시각은 기존처럼 서버가 생성한다. 클라이언트가 보낸 임의의 `createdAt`으로 바뀌지 않는다.
- 경찰청 응답 등 등록 시각이 제공되지 않는 자료에는 등록 시각을 만들어 붙이지 않는다.

사용자가 선택한 방식에 따라 **DB의 UTC 저장값은 유지**했다. 기존 물품의 등록 시각이나 분실·습득 날짜를 일괄 변경하지 않았다. 그림리퍼의 `found_date`도 그대로이며, 이를 실제 습득 날짜로 바꾸는 작업은 별개의 데이터 수정이다.

## 3. DBeaver에서 한국 시간 조회

프로젝트 DB에 읽기 전용 뷰 `found_items_kst`, `lost_items_kst`를 추가했다. 기존 테이블은 8개 그대로이며 뷰가 2개 추가된 것이다. 뷰는 원본 테이블의 최신 값을 조회하므로 새 물품을 등록해도 다시 생성할 필요가 없다.

DBeaver의 `lost_quest` 아래 **Views(뷰)** 항목을 새로고침한 후 다음 SQL을 실행한다.

```sql
SELECT id, title, created_at_kst, found_date
FROM lost_quest.found_items_kst
ORDER BY created_at_utc DESC, id DESC;

SELECT id, title, created_at_kst, lost_date
FROM lost_quest.lost_items_kst
ORDER BY created_at_utc DESC, id DESC;
```

`created_at_kst`는 한국 시간이며 `created_at_utc`는 원본 등록 시각이다. 원본 `found_items.created_at`과 `lost_items.created_at`은 계속 UTC이다. 글 등록 시각은 이 둘을 혼용해 직접 편집하지 않는다.

다른 팀원 PC에서는 Spring Boot로 기본 테이블을 생성한 다음 [05_물품_등록시각_한국시간_조회뷰.sql](SQL/05_물품_등록시각_한국시간_조회뷰.sql)을 실행하면 같은 뷰가 만들어진다. `CREATE OR REPLACE VIEW`이므로 반복 실행할 수 있다. 뷰는 `SQL SECURITY INVOKER`이고 `ALGORITHM = TEMPTABLE`로 읽기 전용이며, 비공개 소유자 답변 해시는 포함하지 않는다.

테이블과 뷰를 구분하려면 다음 SQL을 사용한다.

```sql
SHOW FULL TABLES FROM lost_quest;
```

## 4. 두 물품 테이블의 차이와 사용 흐름

| 항목 | `lost_items` | `found_items` |
| --- | --- | --- |
| 기록의 의미 | 주인이 잃어버린 물건을 찾는 글 | 습득자가 물건을 보관하며 주인을 찾는 글 |
| `user_id` | 분실 글을 등록한 회원 | 습득 글을 등록한 회원 |
| 사건 날짜 | `lost_date`: 잃어버린 날 | `found_date`: 주운 날 |
| 상태 | `LOST`, `RETURNED`, `CLOSED` | `STORED`, `RETURNED`, `CLOSED` |
| 소유자 확인 정보 | 없음 | 확인 질문과 비공개 답변 해시 |
| 글 등록 시각 | `created_at` | `created_at` |

주인이 `lost_items`에 글을 올리면 매칭 기능이 `found_items`와 경찰청 습득물 후보를 비교한다. 사이트 습득물 반환 요청은 `return_requests.found_item_id`로 보관 중인 물품을 참조하고, 요청자가 등록한 분실 글이 있으면 `lost_item_id`로 연결한다. 반환 완료 시 습득 글과 연결된 분실 글의 상태를 함께 `RETURNED`로 바꾼다. 한 물건이 두 테이블에 있다고 해서 단순 중복은 아니다. 서로 다른 사람의 신고가 반환 과정을 통해 연결되는 구조다.

## 5. 하나로 합칠 수 있는가

통합은 가능하다. 예를 들어 `items` 테이블에 `item_type = LOST/FOUND`, `occurred_date`, `created_at`을 두고, 소유 확인 정보는 습득물에만 사용하도록 설계할 수 있다. 물리적으로 테이블이 하나여도 분실·습득 유형과 각 유형의 권한·상태 검증은 유지해야 한다.

현재 분실물 ID와 습득물 ID는 독립적이어서 같은 숫자가 양쪽에 존재할 수 있다. 통합하려면 새 ID 대응표로 기존 데이터를 옮기고, 반환 요청·매칭 알림 참조, 엔티티·저장소·API, 화면 경로와 검증을 함께 수정해야 한다. 분실·습득 날짜를 합쳐도 글 등록 시각과는 별도로 유지해야 한다.

현재 기능에서는 주인과 습득자의 역할 및 반환 흐름이 분명하므로 두 테이블을 유지하는 것이 적합하다. 이번 날짜·시간 문제를 해결하기 위해 통합할 필요는 없으며, 이번 작업에서도 통합하지 않았다.

## 6. 검증

- 날짜 경계 테스트: UTC `2026-10-09 15:00:00` → 한국 `2026-10-10 00:00:00`; 날짜 기본값·미래 날짜 검증·자정 표시 확인.
- 화면 테스트: 분실·습득 날짜와 서버 등록 시각이 별도로 표시되고, 등록 시각이 없을 때 임의 값이 생기지 않음.
- 실제 MySQL/API 테스트: 임시 분실물·습득물을 등록하여 등록 시각이 요청 전후 실제 시각 안에 있고, API·UTC 저장값·한국 시간 뷰가 같은 순간을 나타냄을 확인. 다시 조회해도 값 유지.
- 임의 클라이언트 등록 시각은 무시되며, 입력한 사건 날짜는 유지됨.
- 기존 물품의 날짜·시각을 유지하고 테스트용 회원·물품·활동 기록은 검증 후 제거.

전체 백엔드 테스트 279개, 프론트엔드 테스트 248개와 프론트엔드 빌드가 통과했다. 수정된 Spring Boot 서버를 MySQL 8.4.11에 연결해 정상 시작했고, 실행 중인 Vite가 수정된 상세 페이지를 제공하는 것도 확인했다.

검증 로그와 상세 결과는 Git에서 제외되는 `.local/item-time-*` 파일에 저장했다.
