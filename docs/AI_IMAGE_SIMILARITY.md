# AI 사진 유사도 — 설계와 1단계 PoC 결과

작성: 2026-10-19 · 브랜치 `feature/ai-image-similarity-poc` · **독립 PoC 단계 (서비스 미통합)**

## 1. 목표와 원칙 (승인된 방향)

| 항목 | 결정 |
| --- | --- |
| 모델 실행 | Python FastAPI + OpenCLIP, `127.0.0.1`에서만 실행, 모델명·가중치 고정, CPU |
| 점수 | 기존 분류·지역·색상·날짜 **100점 체계 유지**. 사진 유사도는 **별도 참고 지표**로만 표시 |
| 순위·알림 | 기존 매칭 순위와 70점 알림 기준 **변경 없음** |
| 실패 시 | 사진 없음·임베딩 실패·서버 중단은 지표만 생략. **기존 점수에 불이익 없음** |
| 임계값 | 임의로 확정하지 않고 실제 사진으로 검증 |
| 1단계 범위 | LOST QUEST 등록 사진끼리. 경찰청 사진 다운로드·캐시는 후속 단계 |
| 개인정보 | 사진 원본을 외부 AI 서비스로 보내지 않음 |
| 안전 | 기존 서버·MySQL 데이터·실행 중인 프로세스 보존. DB 스키마 변경·매칭 코드 통합은 **별도 승인 후** |

사진 유사도는 추천 참고 정보입니다. 소유자 확인·QR·관리자 최종 완료 절차를 대신하거나 완화하지 않습니다. 화면 문구는 "사진이 비슷해요" 수준으로 하고 "AI가 판단/확인했다" 같은 표현을 쓰지 않습니다.

## 2. 구성 (PoC: `ai/image-similarity/`)

```
ai/image-similarity/
  app/config.py      고정 모델·가중치 SHA-256·크기 제한·loopback 설정
  app/embedder.py    이미지 검증·디코딩(EXIF 회전 반영) → OpenCLIP 임베딩(L2 정규화) / 테스트용 FakeEmbedder
  app/main.py        FastAPI: /health, /v1/embeddings, /v1/similarity (문서 화면 비활성)
  app/client.py      백엔드가 따를 호출 계약: 모든 실패를 상태값으로 변환 (예외 없음)
  run_server.py      127.0.0.1 이외 주소 바인딩 거부
  scripts/           download_model, make_samples, evaluate, benchmark, failure_drill
  tests/             32개 자동 테스트
```

- **모델 고정**: `ViT-B-32` / `laion2b_s34b_b79k` · HF `laion/CLIP-ViT-B-32-laion2B-s34B-b79K` 커밋 `1a25a446712ba5ee05982a381eed697ef9b435cf` · `open_clip_model.safetensors` 605,143,316바이트, SHA-256 `ac4f8c4b88af6d963118cbf40ad93176d092abbedfcb752601ae1866352656e6`. 서버는 시작할 때 체크섬을 확인하고 `HF_HUB_OFFLINE=1`로 불러옵니다(실행 중 인터넷 접속 없음).
- **런타임 고정**: Python 3.14.3, torch 2.14.1+cpu, open_clip_torch 3.3.0 등 `requirements.txt`에 버전 고정.
- **입력 검증**: 10MB·4천만 픽셀 초과 거부(413), JPEG·PNG·WebP만 허용(파일 이름·Content-Type이 아닌 실제 디코딩 기준), 손상 파일 400. 사진은 메모리에서만 처리하고 저장·로그 기록하지 않습니다.
- **추론**: 모델 1개를 잠금으로 직렬 사용, CPU 추론은 이벤트 루프 밖 스레드에서 실행해 `/health`가 막히지 않게 합니다.

## 3. 1단계 PoC 검증 결과 (2026-10-19, 실제 실행)

환경: AMD Ryzen AI 5 435 (12 논리 코어), RAM 15GB, Windows, CPU 전용.

### 3.1 처리 시간·메모리 (`scripts/benchmark.py`, 30회)

| 항목 | 결과 |
| --- | --- |
| 모델 로딩 (체크섬 확인 포함) | 7.7초 (서버 기동 후 `/health` OK까지 8.5~9.0초) |
| 메모리 | 로딩 후 RSS 약 950MiB, 측정 중 최대 976MiB (서버 프로세스 약 996MiB) |
| 512×512 JPEG 1장 | p50 74ms · p95 90ms |
| 4000×3000 JPEG 1장 (휴대폰 사진 크기) | p50 192ms · p95 256ms |

### 3.2 동일·유사·무관 비교 (`scripts/evaluate.py`, 합성 샘플 26쌍)

샘플은 Pillow로 그린 **합성 물품 이미지**입니다(인터넷 사진·서비스 DB 사진 미사용). 같은 물건은 잘라내기·회전·어둡게+강한 JPEG 압축·흐림·배경 교체로 만들었습니다.

| 라벨 | 쌍 | 최소 | 평균 | 최대 |
| --- | --- | --- | --- | --- |
| same (같은 물건) | 15 | 0.758 | 0.920 | 0.971 |
| similar (같은 종류, 다른 물건) | 3 | 0.753 | 0.844 | 0.901 |
| unrelated (다른 종류) | 8 | 0.521 | 0.587 | 0.665 |

- **무관한 물건은 뚜렷이 구분**됩니다: similar 최소(0.753) − unrelated 최대(0.665) = **+0.089**.
- **같은 물건과 비슷한 다른 물건은 겹칩니다**: same 최소(0.758, 같은 지갑을 다른 배경에서) < similar 최대(0.901, 남색 가방 vs 검은 가방). 즉 이 모델은 "같은 종류·비슷한 모양"은 잘 잡지만 **"바로 그 물건"인지는 판단하지 못합니다.** 참고 지표로만 쓰는 결정이 맞다는 근거이며, 소유 확인은 기존 절차가 계속 담당해야 합니다.
- 합성 이미지 결과이므로 **임계값은 아직 정하지 않습니다.** 실제 사진 검증 방법은 `ai/image-similarity/samples/real/README.md`에 정리했습니다(사진 파일은 Git 제외).

### 3.3 장애 훈련 (`scripts/failure_drill.py`, 실제 모델 서버 프로세스) — 12/12 통과

| 상황 | 결과 |
| --- | --- |
| 서버 기동·`/health` | 8.5초 |
| 수신 주소 | `127.0.0.1`만 LISTEN, 추론 중 외부 연결 0건 |
| 같은 물건 vs 무관한 물건 | 0.923 > 0.521 |

| 재시작 | 같은 사진의 벡터 차이 0.0 (완전히 재현), 비교 재개 |

### 3.4 자동 테스트 — `pytest` 32개 통과

API 계약(정규화·결정성·오류 코드·문서 화면 비활성·loopback 외 바인딩 거부·모델 로드 실패 시 503), 클라이언트 상태 변환(타임아웃·연결 실패·4xx/5xx·비정상 응답), 입력 처리(EXIF 회전·PNG/WebP·0 벡터), 실제 모델(고정 모델·차원·재시작 재현성). 핵심 방어 코드(크기 제한, EXIF 회전)를 일부러 제거하면 해당 테스트가 실패하는 것을 확인했습니다.

## 4. 서비스 통합 설계 (다음 단계, 승인 후 진행)

### 4.1 데이터

이미지는 업로드마다 새 UUID 키(`/api/images/{uuid}.ext`)를 받습니다. 그래서 벡터는 **이미지 키 + 모델 버전**에 묶으면 사진 교체 시 "갱신"이 아니라 "새 키의 새 벡터"가 됩니다.

```sql
-- 제안 (아직 적용하지 않음)
CREATE TABLE image_embeddings (
  image_key     VARCHAR(41)  NOT NULL,
  model_version VARCHAR(80)  NOT NULL,   -- 예: ViT-B-32/laion2b_s34b_b79k@1a25a44
  dim           SMALLINT     NOT NULL,
  vector        VARBINARY(2048) NOT NULL, -- float32 x 512, L2 정규화
  status        VARCHAR(16)  NOT NULL,    -- READY / FAILED
  attempts      TINYINT      NOT NULL DEFAULT 0,
  updated_at    DATETIME(6)  NOT NULL,
  PRIMARY KEY (image_key, model_version)
);
```

### 4.2 비동기 생성 (등록 응답 지연 없음)

1. 분실물·습득물 등록/수정이 **커밋된 뒤** `ItemImageChangedEvent(imageKey)`를 처리합니다(`@TransactionalEventListener(AFTER_COMMIT)` + 별도 실행기). 기존 매칭 알림과 같은 방식입니다.
2. 작업자는 DB에서 이미지 바이트를 읽어 임베딩 서버에 보내고 결과를 저장합니다. 실패하면 `FAILED`와 시도 횟수만 기록합니다(최대 3회, 지수 대기).
3. 서버 재시작·장애로 놓친 이미지는 시작 시 및 주기적으로 "벡터 없는 이미지"를 찾아 다시 채웁니다(백필, 한 번에 소량).
4. 등록 API는 임베딩 성공 여부와 무관하게 기존과 똑같이 응답합니다.

### 4.3 수정·삭제·숨김

| 이벤트 | 처리 |
| --- | --- |
| 사진 교체 | 새 키에 대해 생성. 이전 키는 어떤 글에서도 참조하지 않으면 벡터 삭제 |
| 사진 삭제(`removeImage`) | 이전 키 벡터 삭제(참조가 없을 때) |
| 글 삭제(소프트 삭제)·관리자 숨김 | 비교 대상에서 즉시 제외(쿼리 조건), 벡터는 정리 작업에서 삭제 |
| 모델 변경 | `model_version`이 다르므로 새 벡터를 만들고 이전 버전 벡터는 일괄 삭제 |

### 4.4 매칭 화면 표시 (점수 영향 없음)

- `MatchingService`의 기존 순위 계산은 그대로 둡니다. 순위가 정해진 결과 목록에 대해서만 `photoSimilarity` 참고 값을 덧붙입니다(두 사진의 벡터가 모두 있을 때만, DB에서 읽어 메모리에서 내적 계산 — 모델 서버 호출 없음).
- 응답 예: `"photoSimilarity": { "status": "READY", "level": "HIGH" }` 또는 `{ "status": "NO_IMAGE" }` (상태: `READY`·`PENDING`·`NO_IMAGE`·`UNAVAILABLE`). 실제 코사인 값을 화면에 노출할지, 구간(높음/보통/낮음)만 보여 줄지는 실제 사진 보정 후 결정합니다.
- 매칭 화면에서는 물품 선택 후 **매칭 시작**을 눌러야 1차 텍스트 조건 매칭을 실행합니다. 추천 결과가 있을 때 **AI 이미지 매칭**을 선택할 수 있으며, 현재는 서비스 연결 준비 중이라는 안내만 표시합니다. 이 버튼은 PoC 서버를 호출하지 않습니다. 물품 변경·1차 재실행 시 2차 선택을 초기화합니다.
- 프론트 표시 UI는 준비되어 있습니다(`frontend/src/components/PhotoSimilarityIndicator.tsx`). 기본값은 숨김이며 `VITE_FEATURE_AI_PHOTO_SIMILARITY=true`이고 사용자가 2차 버튼을 선택했을 때만 표시됩니다. 서버 데이터가 없으면 `UNAVAILABLE`로 표시하고, `READY`라도 실제 값이 없으면 점수를 표시하지 않습니다.
- 70점 알림 기준·정렬·`score`·`scoreBreakdown`은 변경하지 않습니다.

### 4.5 장애 격리

- 임베딩 서버가 꺼져 있어도 등록·조회·매칭·알림·반환은 기존과 동일합니다. 화면에는 사진 지표만 표시되지 않습니다.
- 백엔드 → 임베딩 서버 호출은 짧은 타임아웃(예: 3초)과 동시 요청 수 제한을 둡니다. 임베딩 서버는 `127.0.0.1`에만 열려 ngrok·외부로 노출되지 않습니다.

## 5. 남은 결정·위험

1. **실제 사진 보정**: 팀 사진 세트(물품 10개 이상 × 상황 3장 이상)로 같은/비슷한/무관한 분포를 확인한 뒤 표시 구간을 정합니다.
2. **"같은 물건" 판별 한계**: 현재 모델은 같은 종류의 다른 물건과 같은 물건을 구분하지 못합니다. 지표 문구는 "비슷한 종류·모양"으로 제한합니다.
3. **자원**: 서버 메모리 약 1GB. 발표 PC에서는 기존 Spring Boot·MySQL·Vite와 함께 실행해도 되는지(RAM 15GB) 확인이 필요합니다.
4. **통합 승인 필요 항목**: `image_embeddings` 테이블 추가(운영 DB 마이그레이션), 백엔드 이벤트·작업자 코드, 매칭 응답 필드 추가, 프론트 표시 활성화(UI는 준비됨, 기본 숨김).

## 6. 발표 시 설명 포인트

- 기존 규칙 점수는 그대로 두고, 사진은 **참고 지표로만** 더해 "설명 가능한 점수"를 유지합니다.
- 사진은 PC 밖으로 나가지 않습니다. 고정된 공개 모델을 로컬 CPU에서 실행합니다.
- 실험 결과 "다른 종류"는 확실히 구분하지만 "같은 물건 vs 비슷한 다른 물건"은 구분하지 못했습니다. 그래서 AI 결과로 소유를 판단하지 않고, 기존 소유자 확인·QR 절차를 유지합니다.
