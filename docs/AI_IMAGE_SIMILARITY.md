# AI 사진 유사도 — 설계와 1단계 PoC 결과

작성: 2026-10-19 · **브라우저 이미지 비교 적용 / Python OpenCLIP은 독립 PoC 유지**

## 현재 PC에 적용한 실행 구성

- `npm run setup:vision`으로 DINOv2-small q8(가중치 24,446,700바이트), CLIP ViT-base-patch32 q8(153,695,702바이트), 로컬 ONNX WASM 런타임을 설치합니다. 고정 모델 출처·리비전은 `frontend/config/models.example.json`, 무결성 확인은 각 모델의 `assets.json`을 사용합니다. 재검증: `node scripts/setup-vision.mjs --check` (`frontend/`에서 실행).
- CPU/WASM 단일 스레드로 사용합니다. 모델 파일은 `frontend/public/models/`, 런타임은 `frontend/public/onnx/`에 두며 Git에서 제외합니다. 기본 설정은 로컬 파일만 사용합니다. 사진을 외부 AI 서비스에 전송하지 않으며 Ollama·GPU·Python 모델 서버는 필요하지 않습니다.
- `/matches`: 내 분실물 선택 → **매칭 시작**(버튼 하나). 결과가 나오면 **사진이 있는 추천 항목에만** 카드마다 **AI 사진 비교** 버튼이 생깁니다(내 분실물에도 실제 사진이 있어야 함). 버튼을 누르면 매칭 결과 위에 `/image-analysis`와 같은 비교 화면이 겹쳐 열리고, 내 분실물 사진(A)과 그 습득물 사진(B)을 불러와 바로 비교한 뒤 가운데에 종합 유사도(외형 70% + 색상 30%, CLIP 종류 확인)를 크게 보여 줍니다. 닫으면 매칭 결과로 그대로 돌아갑니다. 사진은 이 기기에서만 비교하며 기존 점수·순위·70점 알림 기준·소유 확인 절차는 변경하지 않습니다.
- 자체 물품의 공개 상세를 다시 읽어 숨김·종료·사진 교체 여부를 확인합니다. 예시 이미지·사진 없음은 추론하지 않습니다. 경찰청 사진은 아래의 인증된 이미지 캐시 API로 읽으며 2차에서 경찰청 목록·상세 OpenAPI를 추가 호출하지 않습니다. 사진 조회·추론 실패는 해당 카드만 `UNAVAILABLE`로 표시하고 다른 비교와 1차 결과를 유지합니다. 2차 작업은 DB에 기록하거나 물품을 수정하지 않습니다.
- 한 번에 한 후보씩 비교하고, 취소·물품 변경·1차 재실행 시 늦게 도착한 결과를 무시합니다. 비교가 끝나면 모델 Worker를 종료해 메모리를 해제합니다. DB 벡터 테이블이나 백필 작업은 추가하지 않습니다.
- `/image-analysis`: 파일 두 장을 직접 선택해 DINOv2 외형과 색상을 비교하고 CLIP으로 종류를 자동 판별합니다. 종류가 불확실하면 종합 결과를 보류합니다. 사용자가 종류를 직접 선택해 재비교할 수 있습니다. 이 화면도 완료 후 Worker를 해제합니다.
- **텍스트 의미 참고값 (2026-10-20, 발표 전 A안)**: `npm run setup:text`로 multilingual-e5-small q8(가중치 118,308,185바이트, 고정 리비전은 `frontend/config/text-model.json`)을 설치합니다. **매칭 시작** 후 서버의 기존 결과(40점 이상, 최대 10개, 매칭도순)를 먼저 표시하고, 브라우저에서 제목·공개 설명·분류·색상의 의미 유사도를 카드마다 "텍스트 의미 n% · 참고값"으로 덧붙입니다. 이 값은 순서·필터·개수·점수·알림에 반영하지 않습니다. 모델이 없거나 실패하면 값 없이 안내 문구만 표시합니다. 소유 확인 질문·답변, 토큰, 사용자 번호는 비교 문장에 넣지 않습니다.
- **이름 우선 추천 순서 (2026-10-20)**: 추천 목록(`GET /api/lost-items/{id}/matches`)만 물품 이름에서 판별한 종류(`ItemKind`)로 먼저 묶어 정렬합니다. 같은 종류 → 종류 불명 → 다른 종류 순이고, 각 묶음 안에서는 기존 매칭도 순입니다. 예: "검은색 우산"에는 65점 "블랙 3단 우산"이 100점 "검은 후드집업"보다 먼저 나옵니다. 100점 점수 계산, 40점 기준, 최대 10개, 매칭 알림(70점, 점수순)은 바꾸지 않았습니다.
  - 이름이 분명히 다른 종류(예: 우산을 찾을 때 낚싯대·후드집업)는 추천 목록에서 뺍니다. 종류를 알 수 없는 후보는 남깁니다. 낚시·골프 용품을 종류 낱말에 추가했습니다.
  - 화면 표시: 응답의 `lostItem.nameKind`(예: "우산")와 `matches[].nameMatch`(`SAME_KIND`/`UNKNOWN_KIND`)로 같은 종류 후보는 큰 카드와 "이름 일치" 표시로 강조하고, 종류를 알 수 없는 후보는 "그 밖의 후보" 아래 작은 카드(사진·제목·매칭도·지역·날짜)로 보여 줍니다. 분실물 이름으로 종류를 알 수 없으면 기존 목록 그대로입니다. 점수에는 반영하지 않습니다.
  - 경찰청 조회는 한 번에 50개(지역 최대 2회 + 전국 1회)만 가져오므로, 분실물 분류 이름이 경찰청 분류와 같지 않을 때(예: '액세서리', '기타') 추천 목록 조회에 한해 이름에서 읽은 종류를 경찰청 분류로 바꿔 조회합니다(예: 우산 → 기타물품, 낚시·골프 → 스포츠용품). 열쇠·시계·카드·물병처럼 여러 분류에 걸치는 종류는 바꾸지 않습니다. 알림용 조회는 기존 그대로입니다.
- 모델 추론은 프론트엔드에서 실행합니다. 경찰청 이미지 중계를 처음 적용할 때만 최신 백엔드를 실행해야 하며, DB 스키마 변경은 없습니다. `VITE_FEATURE_AI_PHOTO_SIMILARITY`는 예전 서버 지표용 플래그이며 명시적으로 실행하는 브라우저 비교에는 필요하지 않습니다.

### 경찰청 사진 중계·캐시 (2026-10-20)

- `GET /api/public-items/image?url=<encoded police image URL>`: JWT 인증이 필요합니다. 로그인하지 않은 요청은 외부 다운로드 전에 401로 거부됩니다. 브라우저는 JWT를 이 백엔드 경로에만 보내고 경찰청에는 직접 이미지 픽셀 요청이나 인증 정보를 보내지 않습니다.
- 기존 `PoliceImagePolicy`가 허용하는 `https://minwon24.police.go.kr/lost112/find/getOpenapiAttachFileImage/...` 주소만 허용합니다. 쿼리·fragment·다른 포트/호스트/프로토콜·리다이렉트는 거부합니다. 외부 요청에 사용자의 JWT·쿠키·헤더를 전달하지 않습니다.
- 이미지당 10MiB, 연결 3초·읽기 유휴 5초·네트워크 전체 10초 제한입니다. JPEG·PNG·WebP의 Content-Type, 시그니처, 안전한 실제 디코드를 확인합니다. HTML·손상·과대 해상도 이미지는 거부합니다.
- 서버 메모리 캐시는 최대 12시간, 32MiB, 128개 LRU입니다. 크기 제한으로 더 일찍 퇴출될 수 있고 서버 재시작 시 비워집니다. 브라우저에는 `Cache-Control: max-age=43200, private`를 반환합니다. 강제 갱신 옵션은 제공하지 않습니다.
- 같은 주소의 동시 요청은 진행 중인 다운로드 하나를 공유합니다. 실패 결과도 1분간 유지합니다. 별도 이미지 예산은 JVM당 동시 2개·분당 30회·한국 날짜 기준 하루 1,000회이며, 실패를 포함한 실제 다운로드 시도만 계산합니다. 기존 OpenAPI 목록 캐시·호출 예산은 변경하지 않습니다.
- `X-Police-Image-Cache: MISS/HIT`로 서버 재사용 여부를 검증할 수 있습니다. 이 API는 DB나 디스크에 사진을 저장하지 않습니다. 목록·홈·1차 매칭에서 이 API를 미리 호출하지 않고 사용자가 2차 버튼을 눌렀을 때만 호출합니다.

아래 내용은 기존 Python OpenCLIP 실험 기록과 아직 적용하지 않은 서버 통합 설계입니다. 현재 화면의 DINOv2 참고값과 혼동하지 마세요.

## 2. 구성 (PoC: `ai/image-similarity/`)

```
ai/image-similarity/
  app/config.py      고정 모델·가중치 SHA-256·크기 제한·loopback 설정
  app/embedder.py    이미지 검증·디코딩(EXIF 회전 반영) → OpenCLIP 임베딩(L2 정규화) / 테스트용 FakeEmbedder
  app/main.py        FastAPI: /health, /v1/embeddings, /v1/similarity (문서 화면 비활성)
  app/client.py      백엔드가 따를 호출 계약: 모든 실패를 상태값으로 변환 (예외 없음)
  run_server.py      127.0.0.1 이외 주소 바인딩 거부
  scripts/           download_model, make_samples, evaluate, benchmark, failure_drill
  tests/             32개 자동 테스트
```

- **모델 고정**: `ViT-B-32` / `laion2b_s34b_b79k` · HF `laion/CLIP-ViT-B-32-laion2B-s34B-b79K` 커밋 `1a25a446712ba5ee05982a381eed697ef9b435cf` · `open_clip_model.safetensors` 605,143,316바이트, SHA-256 `ac4f8c4b88af6d963118cbf40ad93176d092abbedfcb752601ae1866352656e6`. 서버는 시작할 때 체크섬을 확인하고 `HF_HUB_OFFLINE=1`로 불러옵니다(실행 중 인터넷 접속 없음).
- **런타임 고정**: Python 3.14.3, torch 2.14.1+cpu, open_clip_torch 3.3.0 등 `requirements.txt`에 버전 고정.
- **입력 검증**: 10MB·4천만 픽셀 초과 거부(413), JPEG·PNG·WebP만 허용(파일 이름·Content-Type이 아닌 실제 디코딩 기준), 손상 파일 400. 사진은 메모리에서만 처리하고 저장·로그 기록하지 않습니다.
- **추론**: 모델 1개를 잠금으로 직렬 사용, CPU 추론은 이벤트 루프 밖 스레드에서 실행해 `/health`가 막히지 않게 합니다.

### 3.2 동일·유사·무관 비교 (`scripts/evaluate.py`, 합성 샘플 26쌍)

샘플은 Pillow로 그린 **합성 물품 이미지**입니다(인터넷 사진·서비스 DB 사진 미사용). 같은 물건은 잘라내기·회전·어둡게+강한 JPEG 압축·흐림·배경 교체로 만들었습니다.

| 라벨 | 쌍 | 최소 | 평균 | 최대 |
| --- | --- | --- | --- | --- |
| same (같은 물건) | 15 | 0.758 | 0.920 | 0.971 |
| similar (같은 종류, 다른 물건) | 3 | 0.753 | 0.844 | 0.901 |
| unrelated (다른 종류) | 8 | 0.521 | 0.587 | 0.665 |

- **무관한 물건은 뚜렷이 구분**됩니다: similar 최소(0.753) − unrelated 최대(0.665) = **+0.089**.
- **같은 물건과 비슷한 다른 물건은 겹칩니다**: same 최소(0.758, 같은 지갑을 다른 배경에서) < similar 최대(0.901, 남색 가방 vs 검은 가방). 즉 이 모델은 "같은 종류·비슷한 모양"은 잘 잡지만 **"바로 그 물건"인지는 판단하지 못합니다.** 참고 지표로만 쓰는 결정이 맞다는 근거이며, 소유 확인은 기존 절차가 계속 담당해야 합니다.
- 합성 이미지 결과이므로 **임계값은 아직 정하지 않습니다.** 실제 사진 검증 방법은 `ai/image-similarity/samples/real/README.md`에 정리했습니다(사진 파일은 Git 제외).

### 3.4 자동 테스트 — `pytest` 32개 통과

API 계약(정규화·결정성·오류 코드·문서 화면 비활성·loopback 외 바인딩 거부·모델 로드 실패 시 503), 클라이언트 상태 변환(타임아웃·연결 실패·4xx/5xx·비정상 응답), 입력 처리(EXIF 회전·PNG/WebP·0 벡터), 실제 모델(고정 모델·차원·재시작 재현성). 핵심 방어 코드(크기 제한, EXIF 회전)를 일부러 제거하면 해당 테스트가 실패하는 것을 확인했습니다.

## 4. 서비스 통합 설계 (다음 단계, 승인 후 진행)

### 4.1 데이터

이미지는 업로드마다 새 UUID 키(`/api/images/{uuid}.ext`)를 받습니다. 그래서 벡터는 **이미지 키 + 모델 버전**에 묶으면 사진 교체 시 "갱신"이 아니라 "새 키의 새 벡터"가 됩니다.

```sql
-- 제안 (아직 적용하지 않음)
CREATE TABLE image_embeddings (
  image_key     VARCHAR(41)  NOT NULL,
  model_version VARCHAR(80)  NOT NULL,   -- 예: ViT-B-32/laion2b_s34b_b79k@1a25a44
  dim           SMALLINT     NOT NULL,
  vector        VARBINARY(2048) NOT NULL, -- float32 x 512, L2 정규화
  status        VARCHAR(16)  NOT NULL,    -- READY / FAILED
  attempts      TINYINT      NOT NULL DEFAULT 0,
  updated_at    DATETIME(6)  NOT NULL,
  PRIMARY KEY (image_key, model_version)
);
```

### 4.2 비동기 생성 (등록 응답 지연 없음)

1. 분실물·습득물 등록/수정이 **커밋된 뒤** `ItemImageChangedEvent(imageKey)`를 처리합니다(`@TransactionalEventListener(AFTER_COMMIT)` + 별도 실행기). 기존 매칭 알림과 같은 방식입니다.
2. 작업자는 DB에서 이미지 바이트를 읽어 임베딩 서버에 보내고 결과를 저장합니다. 실패하면 `FAILED`와 시도 횟수만 기록합니다(최대 3회, 지수 대기).
3. 서버 재시작·장애로 놓친 이미지는 시작 시 및 주기적으로 "벡터 없는 이미지"를 찾아 다시 채웁니다(백필, 한 번에 소량).
4. 등록 API는 임베딩 성공 여부와 무관하게 기존과 똑같이 응답합니다.

### 4.3 수정·삭제·숨김

| 이벤트 | 처리 |
| --- | --- |
| 사진 교체 | 새 키에 대해 생성. 이전 키는 어떤 글에서도 참조하지 않으면 벡터 삭제 |
| 사진 삭제(`removeImage`) | 이전 키 벡터 삭제(참조가 없을 때) |
| 글 삭제(소프트 삭제)·관리자 숨김 | 비교 대상에서 즉시 제외(쿼리 조건), 벡터는 정리 작업에서 삭제 |
| 모델 변경 | `model_version`이 다르므로 새 벡터를 만들고 이전 버전 벡터는 일괄 삭제 |

### 4.4 매칭 화면 표시 (점수 영향 없음)

- `MatchingService`의 기존 순위 계산은 그대로 둡니다. 순위가 정해진 결과 목록에 대해서만 `photoSimilarity` 참고 값을 덧붙입니다(두 사진의 벡터가 모두 있을 때만, DB에서 읽어 메모리에서 내적 계산 — 모델 서버 호출 없음).
- 응답 예: `"photoSimilarity": { "status": "READY", "level": "HIGH" }` 또는 `{ "status": "NO_IMAGE" }` (상태: `READY`·`PENDING`·`NO_IMAGE`·`UNAVAILABLE`). 실제 코사인 값을 화면에 노출할지, 구간(높음/보통/낮음)만 보여 줄지는 실제 사진 보정 후 결정합니다.
- 서버 OpenCLIP 지표는 아직 연결하지 않았습니다. 현재 2차 버튼은 위에서 설명한 브라우저 DINOv2 비교를 실행하며 Python PoC 서버를 호출하지 않습니다.
- 공통 참고 지표 UI(`frontend/src/components/PhotoSimilarityIndicator.tsx`)는 브라우저에서 실제 측정한 외형·색상 값 또는 기존 상태를 표시합니다. 기존 서버용 `READY`에 값이 없으면 점수를 만들지 않습니다.
- 70점 알림 기준·정렬·`score`·`scoreBreakdown`은 변경하지 않습니다.

### 4.5 장애 격리

- 임베딩 서버가 꺼져 있어도 등록·조회·매칭·알림·반환은 기존과 동일합니다. 화면에는 사진 지표만 표시되지 않습니다.
- 백엔드 → 임베딩 서버 호출은 짧은 타임아웃(예: 3초)과 동시 요청 수 제한을 둡니다. 임베딩 서버는 `127.0.0.1`에만 열려 ngrok·외부로 노출되지 않습니다.

## 5. 남은 결정·위험

1. **실제 사진 보정**: 팀 사진 세트(물품 10개 이상 × 상황 3장 이상)로 같은/비슷한/무관한 분포를 확인한 뒤 표시 구간을 정합니다.
2. **"같은 물건" 판별 한계**: 현재 모델은 같은 종류의 다른 물건과 같은 물건을 구분하지 못합니다. 지표 문구는 "비슷한 종류·모양"으로 제한합니다.
3. **자원**: 서버 메모리 약 1GB. 발표 PC에서는 기존 Spring Boot·MySQL·Vite와 함께 실행해도 되는지(RAM 15GB) 확인이 필요합니다.
4. **통합 승인 필요 항목**: `image_embeddings` 테이블 추가(운영 DB 마이그레이션), 백엔드 이벤트·작업자 코드, 매칭 응답 필드 추가, 프론트 표시 활성화(UI는 준비됨, 기본 숨김).

## 6. 발표 시 설명 포인트

- 기존 규칙 점수는 그대로 두고, 사진은 **참고 지표로만** 더해 "설명 가능한 점수"를 유지합니다.
- 사진은 PC 밖으로 나가지 않습니다. 고정된 공개 모델을 로컬 CPU에서 실행합니다.
- 실험 결과 "다른 종류"는 확실히 구분하지만 "같은 물건 vs 비슷한 다른 물건"은 구분하지 못했습니다. 그래서 AI 결과로 소유를 판단하지 않고, 기존 소유자 확인·QR 절차를 유지합니다.
